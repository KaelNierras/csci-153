The premise of this course

The agent writes the code.
You own the judgment.

What the agent is good at
  • Producing a lot of correct-ish markup fast
  • Remembering syntax you would look up
  • Refactoring on instruction
  • Boilerplate: forms, tables, layouts, config
  • Explaining unfamiliar code back to you
What stays yours
  • Deciding what the screen is for
  • Knowing when the output is quietly wrong
  • Accessibility, states, and edge cases it skipped
  • Naming the fix precisely enough to be actioned
  • Taking responsibility for what ships

This is why the module leads with design principles, not with prompts. You cannot review output you cannot evaluate. Everything in Lesson 1.1 exists so that Lesson 1.2 is not guesswork.

Lesson 1.1

The part you
cannot delegate

Twenty-two slides of practice you will use in every code review for the rest of your career.

Motivation

"I'm a backend person" is no longer a defense

Cost
Rework is design debt

A misplaced hierarchy is discovered in user testing, after the components, the API shape, and the routes are already built around it.

Speed
The agent needs a target

Generation is cheap now. The bottleneck moved to specifying what good looks like — that specification is design vocabulary.

Trust
Users judge correctness by look

Research repeatedly finds people rate the credibility of a system by its interface before they ever test whether it works.

Practical version for this class: your final web project (20% of your grade) will be used by someone who was not in the room while you built it. That is the whole test.

Vocabulary that actually differs

Four words people use interchangeably, wrongly

TermThe question it answersFailure looks like
UX — user experienceCan a person accomplish their goal here at all?Enrollment takes 11 steps because that is how the database is shaped.
IxD — interaction designWhat happens when I do this, and how do I know?You press Submit and nothing visibly changes for four seconds.
UI — user interfaceWhat are the controls, and are they legible and reachable?Grey 40% text on white; a 22-pixel tap target on mobile.
Visual designDoes it read as one coherent, deliberate system?Six shades of blue, four corner radii, three fonts, one page.

In a code review you will be more useful if you say "this is an interaction-feedback problem, not a color problem" than if you say "it feels off."

Principle 01 · Visual hierarchy

Same content, same components, same colors

What changed

    Nothing was added. No new color, no illustration, no shadow. Only relative size, weight, spacing, and one accent moved.

    Principle 01 · continued

    You have exactly four levers

    Size
    Biggest reads first

    Strongest and bluntest lever. Use it once per screen. If three things are huge, nothing is.

    Weight
    Heavier reads sooner

    Cheaper than size. Two weights is a system; five weights is noise.

    Color
    Saturation pulls the eye

    Your accent is a spotlight. Point it at the one action you want taken.

    Space
    Isolation implies importance

    The most underused lever. Whitespace around an element is a claim about its rank.

    The rule that fixes most student work: decide the single most important element on the screen, then make every other decision relative to it. If you cannot name that element, the screen is not designed yet.

    Principle 02 · Space

    Spacing is a system, not a vibe

    Preview
    Spacing source
    Density comfortable

    Why it matters: arbitrary values look almost-aligned, which reads as sloppy without the viewer knowing why. A scale makes "wrong" impossible to produce by accident — and gives the agent a rule to follow.

    Principle 03 · Alignment

    Every element lines up with something on purpose

    ✕ Common student output
    • Centered headings over left-aligned body text
    • Cards with different internal padding per card
    • Labels centered, values left, in the same table
    • A "close enough" 14px next to a 16px gutter

    The eye has no edge to follow, so the page feels unstable even though nothing is technically broken.

    ✓ What to do instead
    • Pick one alignment edge per region and hold it
    • Center only short, isolated content — a hero, an empty state
    • Numbers align right with tabular-nums
    • Let the grid produce gaps; do not hand-place margins

    Practical rule: if you are typing a margin value on an individual element, ask whether the parent should own that spacing instead.

    Principle 04 · Typography

    Pick a ratio, then never invent a size again

    Scale preview
    Controls
    Base size 16px
    Ratio
    • Three sizes is usually enough for one screen
    • Body text lives at 65 characters per line, give or take 10
    • Line-height moves opposite to size: 1.5 for body, 1.05 for display
    • Big text gets negative letter-spacing; small caps get positive
    Principle 05 · Color

    You need far fewer colors than you think

    The working budget for one product
    One neutral ramp — 5 to 7 steps
    Background, surface, border, muted text, body text. This is 90% of every screen you will ever build.
    One accent
    Primary action, active state, focus. One. If everything is emphasized, nothing is.
    Semantic colors — success, warning, danger
    These are meaning, not decoration. Never reuse your accent as your success color.
    Bias your neutrals

    A pure #808080 grey reads as un-chosen. Tint the neutral ramp a few percent toward your accent's hue and the whole page reads as one deliberate system.

    Dark mode is not an inversion. Pure white text on pure black vibrates; pure black surfaces flatten depth. Lift the ground to a near-black and drop the text off pure white.

    Principle 07 · Accessibility

    The non-negotiable floor

    Costs you nothing if you do it from the start
    • 4.5:1 contrast for body text, 3:1 for large text and UI borders
    • A visible focus ring — never outline: none without a replacement
    • Touch targets ≥ 44 × 44 px, with spacing between them
    • Every input has a persistent label, not just a placeholder
    • Real semantic elements: button for actions, a for navigation
    • Never encode meaning in color alone — pair it with text or an icon
    • Honor prefers-reduced-motion
    The 30-second audit you can run on any screen
    Unplug the mouse
    Tab through the whole flow. If you get lost or trapped, so does a keyboard user.
    Zoom to 200%
    Ctrl/Cmd +. Text should reflow, not clip or overlap.
    Grayscale it
    Is the primary action still obvious? If not, you encoded meaning in hue alone.

    This is also the fastest way to catch agent output. Generated UI is confidently inaccessible — it will hand you placeholder-only inputs and removed focus rings all day.

    Principle 08 · States

    A component is not one thing. It is seven.

    Live previewDEFAULT

    Pick a state

    Students design state 1. Products live in states 2 – 7. Every mark in the laboratory rubric for "states" is about the six you did not think about.

    Principle 08 · continued

    The two states that decide whether your app feels fast

    Loading
    • Under 100ms — show nothing. A flash of spinner is worse than a pause.
    • 100ms – 1s — show the target's shape: a skeleton, not a spinner.
    • Over 1s — show progress and what is happening in words.
    • Keep layout stable: the skeleton occupies the same box the content will.
    • Consider optimistic UI: apply the change instantly, roll back on failure.
    Empty
    • An empty state is your best onboarding surface — it is the first thing a new user sees.
    • Say what goes here, why it is empty, and give the action that fills it.
    • Distinguish never had any from search returned nothing from failed to load. Three different states, three different messages.
    • Never ship the bare string "No data."

    Ask the agent for these explicitly. "Include loading, empty, and error states for this list" is one clause that doubles the usefulness of the output.

    Principle 09 · Forms

    Where most academic projects lose their users

    Seven fixes, in order of payoff
      Principle 10 · Words

      Copy is design material

      Buttons say what happens
      Instead ofWrite
      SubmitEnroll in 3 subjects
      OKDelete draft
      Yes / NoDiscard changes / Keep editing
      Click hereView your schedule

      Then the confirmation echoes the verb: press Publish, see Published.

      The error message formula
      [what went wrong] + [why] + [the exact next action]

      "Error: invalid input"

      "That student number is 8 digits. Yours has 7 — check for a missing leading zero."

      • No apologies, no "Oops!", no blame
      • Name the field, not the exception class
      • Speak the user's vocabulary: notifications, not webhook config
      Principle 11 · Nielsen's ten

      The industry's shared vocabulary for "this is broken"

      • Visibility of system status — always tell the user what is happening
      • Match to the real world — their words, their concepts, their order
      • User control & freedom — a clearly marked exit, undo, cancel
      • Consistency & standards — same thing, same name, same place
      • Error prevention — better than any error message
      • Recognition over recall — show options, don't demand memory
      • Flexibility & efficiency — shortcuts for the experienced
      • Aesthetic & minimalist design — every extra element dilutes the rest
      • Help users recover from errors — plain language, a way out
      • Help & documentation — findable, task-focused, concrete

      Memorize these ten. In the laboratory activity, a critique that names the heuristic scores; "it looks bad" does not.

      Checkpoint · call the violation

      Five screens. Name what is wrong.

      Principle 12 · Predictable human behavior

      Four laws you can design against

      Hick's law
      More options, slower decisions

      Decision time grows with the number of choices. Group, default, and progressively disclose — a 14-item nav is a design failure.

      Fitts's law
      Big and near is fast

      Time to hit a target depends on its size and distance. Primary actions get to be large and close to where the eye already is.

      Jakob's law
      They expect your app to work like the others

      Users spend most of their time on other sites. Novel navigation is a tax you charge your user, not a feature.

      Miller's law
      About 7 items in working memory

      Chunk long forms and long lists. This is why phone numbers are grouped and why your 20-field form needs sections.

      These are the load-bearing arguments in a design review. "Hick's law — we have eleven top-level items and three of them do the same thing" is a sentence that wins meetings.

      Principle 13 · Responsive

      Breakpoints come from the content, not from device names

      Drag to resize the container 1024px · desktop

      Design the narrow layout first — it forces you to rank content, and that ranking is your hierarchy. Widening a good mobile layout is easy; cramming a desktop layout into a phone is a rewrite.

      Principle 14 · continued
      
      Why three layers instead of one
      
      
      
        
      
          
      
            
      Primitive — the raw value has no opinion

      Semantic — the value gets a job

      Component — the job gets a location

      Process
      
      Wireframe → mockup → build: know when to stop
      
      
      
        
      
          Low fidelity · minutes
          
      Wireframe
      
          
      Boxes, labels, and ranking. Greyscale only — deliberately ugly so people critique structure instead of color.
      
          
      Answer: what is on this screen, and in what order?
      
        
      
        
      
          Mid fidelity · an hour
          
      Mockup
      
          
      Real type scale, real tokens, real copy. Still no interaction. This is where design is actually decided.
      
          
      Answer: does this read correctly at a glance?
      
        
      
        
      
          High fidelity · a session
          
      Prototype in code
      
          
      Real HTML/CSS, real states, real keyboard behavior. With an agent, this is now cheaper than a clickable Figma prototype.
      
          
      Answer: does it hold up when a human uses it?
      
        
      
      
      
      
      
        The agent collapses the last two steps. That is the actual shift in this course: mid-fidelity used to be
        where you stopped because building was expensive. It is not expensive anymore — so your wireframe thinking has to be sharper, not looser.

      The workflow
      
      "Agentic" means you run a loop, not a prompt
      
      
      
        
      
          
          
          
          
          
        
      

        
      
          
      You do
      • State the product, the user, and the one job of the screen
      • Hand over tokens, stack, and constraints
      • Attach the reference: a screenshot, an existing page, a schema
      
          
      Why it decides everything
      A vague context does not produce a vague answer — it produces a confident answer to a different question. Most bad output traces back to this step, not to the model.
      
        
      
        
      
          
      You do
      • Ask for a plan before any code
      • Read it. Correct it. It is 20 seconds against 200 lines of wrong markup
      • Confirm the component inventory and the states
      
          
      Prompt shape
      # before writing any code
List the components you'll build,
the states each one needs, and the
tokens you'll consume. Wait for my
go-ahead.
      
        
      
        
      
          
      You do
      • Let it write the whole thing without interrupting
      • One screen at a time — not the whole app in one shot
      • Keep the tokens file as the single source of truth
      
          
      Watch for
      • Invented colors that are not in your token set
      • Only the default state implemented
      • Placeholder text used as a label
      • Fake data that hides real overflow cases
      
        
      
        
      
          
      You do
      • Run the 8-point design QA (two slides ahead)
      • Tab through it. Zoom to 200%. Check contrast.
      • Resize to 320px wide
      
          
      This is the graded skill
      Generation is free and everyone in the room has it. The differentiator is whether you can find what is wrong in 90 seconds. That is what Lesson 1.1 bought you.
      
        
      
        
      
          
      You do
      • Give measured corrections, not adjectives
      • One theme per turn — layout, then color, then states
      • Stop when it meets the brief; polish is not free
      
          
      Loop, don't restart
      Beginners throw away the conversation and re-prompt from scratch. The context you built is the asset — correct inside it.

      Sequencing
      
      Tokens first, screens second — always
      
      
      
        
      
          
      ✕ Screen-first
      
          
      
            
      1. "Build me a dashboard"
      2. "Now build me a settings page"
      3. "Now a login page"

      Predictable failure modes — memorize these
      
      
      
        
      Confident wrongness
      It never says "I'm unsure"
      Output arrives in the same assured tone whether it is right or invented. Tone carries zero information about correctness.
      
        
      Happy path only
      Six states quietly missing
      Unless you ask, you get the default state and nothing else. This is the most common gap in submitted work.
      
        
      Accessibility
      Contrast and focus quietly dropped
      Removed outlines, placeholder-only labels, decorative divs acting as buttons. Assume it, check it every time.
      
        
      Perfect fake data
      "Juan Dela Cruz", 3 rows
      Every name fits, every list is short, nothing overflows. Real data breaks the layout you just approved.
      
        
      Drift
      Session 4 forgets session 1
      Without a token file in context, each new screen re-invents the design language.
      
        
      Over-delivery
      Features you never asked for
      Extra sections, extra options, extra dependencies. Every one is surface area you must now defend in the exam.

      Watch this next
      
      The ten-minute redesign, live
      
      
      
        
      Minute 0–1 · Take the ugly screen
      A real enrollment page. Screenshot it, paste it, ask for a critique against Nielsen's ten. Read the critique out loud and disagree with at least one point.
      
        
      Minute 1–3 · Tokens
      Ask for a token set only. Neutral ramp, one accent, semantics, type scale on a 1.2 ratio, 4pt spacing. Fix the accent by hand because it will pick something generic.
      
        
      Minute 3–4 · Plan
      "List the components and their states before writing code." Correct the plan — it will forget the error state.
      
        
      Minute 4–7 · Generate
      Full screen, tokens only, all seven states, 320px minimum. Do not interrupt it.
      
        
      Minute 7–9 · Review, out loud
      Tab through it. Resize to 320. Run the contrast check on the muted text — it will fail at least once.
      
        
      Minute 9–10 · One measured correction
      A single precise instruction, and we compare before/after. That is the whole job.
      
      
      
    
      

    
      
      Recap
      
      The loop, in one screen
      
      
      
        
        
          
      • Context — product, user, job, stack, tokens, constraints, real data
        • 
          
      • Plan — components and states, reviewed before any code
        • 
          
      • Generate — one screen, uninterrupted, tokens only
        • 
          
      • Review — the 8-point QA, every time, no exceptions
        • 
          
      • Iterate — measured corrections, one theme per turn
        • 
        
      
        
        
          
      • Explore in the browser, commit from the editor
        • 
          
      • Tokens first, screens second
        • 
          
      • Failure modes are predictable — check for them by habit
        • 
          
      • Keep the prompt log
        • 
          
      • You must be able to explain every line
        • 
        
      
      
      
      
      The through-line: good prompting is design vocabulary written down. Lesson 1.1 is what makes Lesson 1.2 work.

      Your turn

      Laboratory Activity 1 · Week 2 · CA 1
      
      UI Audit & Redesign
      
      
      
        
      
          
      Scenario
      
          
      You are handed a screenshot of a working but poorly designed academic web page — an enrollment form, a grade viewer, or a request portal. It functions. It is unpleasant. Your job is to say precisely why, then prove your diagnosis by rebuilding it.
      
          
      Deliverables
      
          
      
            
      Written critique — 8 to 12 findings
      Each finding names the principle or heuristic violated, quotes the evidence, and states the fix. One sentence each. "It looks bad" earns zero.
      
            
      Token set
      Neutral ramp, one accent, three semantics, type scale with its ratio stated, spacing scale. As CSS custom properties.
      
            
      Redesigned screen — single HTML file
      Tokens only, no hard-coded values, all seven states for the primary component, works at 320px.
      
            
      Prompt log
      Your brief, the corrections you issued, and one thing the agent got wrong that you caught.
      
          
      
        
      
        
      
          
      
            
      Constraints
      
            
        
              
      • No component library, no icon library, no external images
        • 
              
      • Single file, self-contained
        • 
              
      • Must pass all 8 design QA checks
        • 
              
      • Contrast measured and stated in the critique
        • 
            
      
          
      
          
      
            
      Submission
      
            
        
              
      • VSU E-Learning Portal, before the week 3 session
        • 
              
      • SURNAME_A1.zip — critique.md, tokens.css, index.html, prompt-log.md
        • 
            
      
          
      
        
      
      
      
    
      

    
      
      Laboratory Activity 2 · Week 3 · CA 2
      
      Brief → Prototype
      
      
      
        
      
          
      Scenario
      
          
      Pick one screen from the web app you intend to build for your final project. Take it from a blank page to a reviewed, state-complete prototype using the full agentic loop — and document the loop as you go.
      
          
      Deliverables
      
          
      
            
      Design brief
      Product, user, the screen's one job, stack, tokens, constraints, real data shape. Use the builder from this deck.
      
            
      The agent's plan, with your corrections marked
      Show what it proposed and what you changed before allowing it to generate.
      
            
      Two screens: first generation and final
      Both files kept. The diff between them is the actual submission.
      
            
      Completed 8-point QA sheet
      With the failures you found on the first pass written out, and how each was corrected.
      
          
      
        
      
        
      
          
      
            
      The point of this activity
      
            
      Anyone can generate a screen. You are being graded on the gap between generation one and generation two — that gap is the only place your design judgment is visible.
      
          
      
          
      
            
      Feeds directly into
      
            
        
              
      • Module 02 — this screen becomes your first real components
        • 
              
      • The final web project (FP, 20%)
        • 
              
      • The practical exam (PE, 15%)

      How both activities are marked
      
      Rubric · 100 points
      
      
      
        
      
          
      CriterionPtsFull marks looks like
      
          
            
      Diagnostic precision25Every finding names the specific principle or heuristic, cites the evidence, and proposes an actionable fix. No vague aesthetic complaints.
      
            
      Token discipline20Three-layer tokens, no hard-coded values anywhere in the markup, type and spacing both on a stated scale.
      
            
      State completeness20All seven states present and visibly distinct for the primary component; loading, empty, and error all designed rather than defaulted.
      
            
      Accessibility floor15Measured contrast passing AA, visible focus on every control, labels present, keyboard-operable, works at 320px.
      
            
      Loop documentation15Prompt log shows a real plan-review-iterate cycle with at least one agent error you caught and corrected.
      
            
      Craft5Coherent, deliberate, and defensible as a whole. Not templated.
      
                
        
      
      
      
      
      Automatic deductions: any hard-coded hex (−5 each, max −15) · missing focus states (−10) · placeholder used as label (−5) · a prompt log that does not match the submitted code (referred to the integrity policy).
