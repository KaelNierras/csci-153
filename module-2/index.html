exactly once

Where every beginner starts

One big table feels obvious

enrollments — the spreadsheet version
student_no  name          subject   units  teacher
20-1-01234  Maria Cruz    CSci 153  3      Prof. Reyes
20-1-01234  Maria Cruz    CSci 141  3      Prof. Lim
20-1-01234  Maria Cruz    Math 111  5      Prof. Diaz
20-1-05678  Jose Ramos    CSci 153  3      Prof. Reyes
20-1-05678  Jose Ramos    PE 4      2      Coach Uy

Every question is answerable from one place. It reads like the report you eventually want.

Three problems, and they are not stylistic
  • Update. Maria changes her name — three rows to fix, and if you miss one the database now disagrees with itself.
  • Insert. A new subject nobody has enrolled in yet cannot be recorded at all. There is no row to put it in.
  • Delete. Jose drops PE 4 and the only record that PE 4 is worth 2 units disappears with it.

Every one of these is the same bug: a fact is stored more than once, or in the wrong place entirely.

Interactive · one table becomes four

Pulling the facts apart

Step through it each step fixes one specific failure

You do not need the formal definitions of 1NF, 2NF and 3NF to do this well. You need one question, asked repeatedly: "if this fact changes, how many rows do I have to touch?" More than one is the smell.

The vocabulary

Keys, and the three relationships

Two kinds of key
create table subjects (
  id uuid primary key default gen_random_uuid(),
  code text not null,
  units int not null
);

create table enrollment_items (
  enrollment_id uuid references enrollments(id),
  subject_id    uuid references subjects(id),
  primary key (enrollment_id, subject_id)
);

Primary key — this row's identity. Foreign key — a pointer to another table's identity, which the database will not let you break.

One to many · the common case

One student has many enrollments. The foreign key goes on the "many" side — enrollments.student_id. This is the shape you will use most.

Many to many · needs a third table

An enrollment has many subjects; a subject appears in many enrollments. Neither side can hold the key, so enrollment_items exists to hold the pairs.

One to one · rare, and usually a mistake

If two tables have exactly one row each per thing, ask why they are two tables.

When the rule bends

Storing a total, on purpose

Compute it
select sum(s.units)
from enrollment_items i
join subjects s on s.id = i.subject_id
where i.enrollment_id = $1

Cannot be wrong. It is derived from the truth every time you ask.

Costs a join on every read, and the adviser queue reads it for forty students at once.

Store it
enrollments.total_units int not null default 0

One column, instant read, and the queue query gets simple.

And now it can be wrong. Any write that changes the items and forgets the total leaves the database disagreeing with itself.

Enroll's contract has totalUnits on the enrollment, so it is stored — and a trigger maintains it, not the application. That is lesson 3.4. Duplication with an automatic guardian is a decision; duplication maintained by hand is a bug waiting.

Lesson 2.2 · the spine of the semester

Agree the shape
before either side builds

Your backend does not exist yet. You are going to build against it anyway.

What this lesson prevents

Integration day, without a contract

Week 13, 11pm
  • Frontend expects studentId. Backend sends student_id.
  • Frontend expects units as a number. It arrives as "18".
  • Frontend renders subjects[]. Backend returns { data: { subjects: [] } }.
  • Nobody decided what a failed enrollment returns.
  • Both halves are "done". Neither works.
Why it happens

Two people built from one conversation and remembered it differently. Nothing was written down to be wrong against.

The fix is not "communicate better"

Write the shapes in a file both sides can check, before either side starts.

Not hypothetical: your backend is Module 3, and you implement it in sprint 1. That gap is three weeks wide — short enough to be tempting to wait out, which is exactly why this module's gate is running screens on the mock.

Definition

A contract is every shape, agreed and written down

For each operation
What goes in

Path, method, parameters, request body — typed, and which fields are required.

For each operation
What comes back

Every status code and its body shape. Including the failures.

For the whole API
Shared shapes

Reusable schemas — a Student is a Student everywhere, defined once.

The part people skip

The error responses. Teams specify the happy path and discover the failures later — but failures are most of your UI code, and "what does a 409 look like" is the question you cannot answer at 11pm.

The format

OpenAPI, in three minutes

enrollment-api.yaml
openapi: 3.1.0
info: { title: Enrollment API, version: 1.0.0 }

paths:
  /students/{id}/load:
    get:
      operationId: getStudentLoad
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Load'
        '404':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'

components:
  schemas:
    Load:
      type: object
      required: [studentId, totalUnits, subjects]
      properties:
        studentId:  { type: string }
        totalUnits: { type: integer }
        subjects:
          type: array
          items: { $ref: '#/components/schemas/Subject' }
Four things to find
paths
Every URL, and the methods it supports.
operationId
A stable name. It becomes your generated method name — and your Query key.
responses
Keyed by status code. Every code your UI must handle.
components.schemas
Shapes defined once and referenced with $ref.

YAML is indentation-sensitive and unforgiving. Run redocly lint before you commit.

Worked example · 1 of 3

The YAML on the left is the exchange on the right

contract/openapi.yaml
/students/{studentId}/enrollment/items:
  post:
    operationId: addEnrollmentItem
    parameters:
      - name: studentId
        in: path          # goes in the URL
        required: true
        schema: { type: string, format: uuid }
    requestBody:
      required: true
      content:
        application/json:
          schema:
            type: object
            required: [term, subjectId]
            properties:
              term:      { type: string }
              subjectId: { type: string, format: uuid }
    responses:
      '201':
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/Enrollment'
What actually goes over the wire

{

  "subjectId": "9a2e-…"
}

──────────────────────────────

Content-Type: application/json

Read them together until the mapping is boring: path parameter → the URL, requestBody → what you send, responses.'201'.schema → what you get back. Everything else in the file is a variation on those three.

Worked example · 2 of 3

$ref is the only thing stopping this file from rotting

Written out every time
'200':
  schema:
    type: object
    properties:
      id:         { type: string }
      totalUnits: { type: integer }
      status:     { type: string }

'201':
  schema:
    type: object
    properties:
      id:         { type: string }
      totalUnits: { type: integer }
      status:     { type: string }   # forgot 'returned'
                            # over here

Nine operations return an Enrollment. Change one field and you edit nine places — and miss one.

Defined once, referenced everywhere
components:
  schemas:
    Enrollment:
      type: object
      required: [id, studentId, term, status, totalUnits]
      properties:
        id:         { type: string, format: uuid }
        totalUnits: { type: integer }
        status:
          type: string
          enum: [draft, submitted, approved, returned]

# then, in every operation that returns one:
'200':
  schema:
    $ref: '#/components/schemas/Enrollment'

One edit. Nine operations. The generated TypeScript follows automatically.

enum is doing real work here. It is the difference between status: string — which happily permits "aproved" — and a generated union type that refuses to compile the typo.

Worked example · 3 of 3 · this is Activity 4

From one sentence to one operation

The requirement, as your spec states it

“An adviser can return a submitted enrollment to the student with a reason, which the student sees.”

1 · What is acted on?
An enrollment, by id → /enrollments/{enrollmentId}/return
2 · A read, or a change?
A change → post, not get
3 · What has to be sent?
The reason — and it has to be useful, so minLength
4 · How can it fail?
Not your advisee · already decided · reason too short
The operation those four answers produce
/enrollments/{enrollmentId}/return:
  post:
    operationId: returnEnrollment
    parameters:
      - { name: enrollmentId, in: path, required: true }
    requestBody:
      required: true
      content:
        application/json:
          schema:
            type: object
            required: [reason]
            properties:
              reason:
                type: string
                minLength: 10
                description: Shown to the student verbatim.
    responses:
      '200': # the updated Enrollment
      '403': # not your advisee
      '409': # already decided
      '422': # reason too short

minLength: 10 is a decision, not a detail. It is why the adviser's textarea has a character counter (Lesson 4.4) and why the database has a CHECK constraint (Lesson 3.4). One line here becomes two enforcement points later.

The half everybody skips

A 422 you did not design is a screen you cannot build

Documented, with an example body
'422':
  description: |
    UNIT_CEILING — adding this subject
    would exceed 21 units (R2).
  content:
    application/json:
      schema:
        $ref: '#/components/schemas/Error'
      examples:
        unitCeiling:
          value:
            code: UNIT_CEILING
            message: Adding CSci 153 would put
              you at 24 units. The limit is 21.
            details: { attempted: 24, limit: 21 }

Every error in this contract has the same three keys, so the client has one error path rather than one per endpoint.

What each key buys you
code
What the UI branches on. Machine-readable, never translated, never reworded.
message
What the user reads. Written by whoever wrote the rule, not invented by the frontend at 11pm.
details
The numbers the UI needs to render a meter, highlight a row, or fill in a blank.

The examples block is not decoration — Prism returns it. Send Prefer: code=422 to the mock and your error screen renders that exact body today, with no backend. That is how you build a failure state before the failure exists.

Two ways round

Contract-first vs code-first

Code-first

Build the backend, then generate docs from what you built.

The spec describes whatever happened — bad field names included.

The frontend waits for the backend.

Fine solo.

Contract-first

Agree the spec, then both halves build to it.

The spec is a decision, reviewed while it is still cheap to change.

Both halves start on day one; the frontend runs on a mock.

Necessary as soon as two people are involved — your situation.

This is why the contract is a group deliverable in Activity 4, and why a PR touching it needs the other side's approval.

Interactive · generated types

Types are generated, never hand-written

Toggle a field and watch the TypeScript change openapi-typescript
Why not just write the interface?

A hand-written mirror drifts silently. The backend makes a field nullable, your interface still says string, TypeScript still compiles — and the app crashes on the one null record.

The command
npx openapi-typescript contract/openapi.yaml \
  -o contract/generated/schema.d.ts

Commit the output. CI re-runs it and fails if yours is stale, so it can never quietly disagree with the spec.

A pattern worth naming now

One source of truth, and everything else downstream

How you run today

The mock is what makes the gap survivable

Prism — a whole fake server
npx @stoplight/prism-cli mock contract/openapi.yaml

Serves invented responses that match your spec at localhost:4010. Point your base URL at it and the app runs end to end.

Best for building screens by hand — click around, everything responds.

MSW — interception, in tests
http.get('/students/:id/load', () =>
  HttpResponse.json({
    studentId: 'S-2041',
    totalUnits: 18,
    subjects: [ /* … */ ]
  })
)

Intercepts requests inside tests, so you choose exactly what comes back — including the 404 and 500 you cannot trigger on demand.

Mock the failures, not just the successes — the empty list, the 404, the 500, the slow response. Those states are most of your UI code.

The spec is the best context you can hand an agent

Without the spec
"Write a function to fetch a
student's enrolled subjects."

The agent invents the URL, the field names, the error shape. You find out at integration.

With the spec pasted in
"Here is our OpenAPI spec.
Implement getStudentLoad using
our typed client, handling every

Correct path, types, and error handling — because none of it was a guess.

Bad agent output is usually missing context, not a weak model. The spec removes the biggest guess: what shape is the data?

Lesson 2.3 · one session

A test that has
never failed
proves nothing

Enough Vitest to not be lost in Module 4.

No learning outcome requires this
The anatomy

Three words, and one assertion

src/lib/rules/units.test.ts
describe('canAddSubject', () => {
  it('R2 · rejects an add past the ceiling', () => {
    const enrolled = [six(), six(), six()]  // 18 units

    const result = canAddSubject(six(), enrolled, 'draft')

    expect(result).toMatchObject({
      ok: false,
      code: 'UNIT_CEILING'
    })
  })
})
Read it as a sentence
  • describe — the thing under test
  • it — one claim about it, in words
  • expect — the claim, in code

Arrange, act, assert. Every test in the file has those three parts in that order.

The name is half the value. "returns an object" tests the language. "R2 rejects an add past the ceiling" tests a decision somebody made — and when it fails, the name alone tells you what broke.

Interactive · the run, and a deliberate break

Green means nothing until you have seen red

npm run test then break the rule on purpose

Change the ceiling to 24 and two tests fail with useful messages. That is the proof the tests are connected to the code. A suite that has never gone red might be asserting nothing at all.

Where the value is

Test the rules, not the framework

Worth testing
  • Pure functions with rules in them — the unit ceiling, capacity, duplicate detection
  • The boundaries — exactly 21 units, an empty array, a subject at capacity
  • Anything you got wrong once — a test is how a bug stays fixed

Enroll has 11 tests, all of them on lib/rules/.

Not worth your time here
  • That React renders a <div>
  • That map maps
  • Getters and setters with no logic in them
  • Chasing 100% coverage for its own sake

Coverage measures lines executed, not claims verified. 100% coverage with weak assertions is a comfortable lie.

The off-by-one test — an add landing exactly on 21 is allowed — is the most valuable one in the file. Boundaries are where bugs live, which is why every rule gets a test on each side of its edge.

The progression

Three kinds of test, arriving in order

KindWhenWhat it proves, and what it costs
UnitNow · 3.8 One function does what its name claims. Milliseconds to run, so you run them constantly.
ComponentModule 4 A component renders the right thing for a given state. Needs a fake DOM, so slower and more fragile.
End to endLesson 4.6 A real browser completes a real flow against a real backend. The only kind that proves the app works — and slow enough that you keep few of them.

Your project specs require Vitest and Playwright in CI, and §12 makes test-cases-as-issues a graded workflow. This session is the floor, not the whole story — Module 4 finishes it.
