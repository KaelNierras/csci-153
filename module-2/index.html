The problem it solves

What happens without it

Zipping folders

final.zip, final2.zip, final_FINAL.zip, final_use_this_one.zip

Two people edit the same file. One of them loses an afternoon and does not find out until the demo.

Nobody can answer "when did this break, and what changed?"

"Who wrote this part" is a matter of memory and argument.

One repository

Every change is dated, attributed, and reversible.

Two people editing different files never collide at all. Editing the same file is detected, not silently lost.

git log answers the "when did this break" question in seconds.

Contribution is evidence, not recollection — which matters when a group project carries an individual grade.

This is why every member needs commits. Not as bureaucracy — the commit history is the only durable record of who did what.

The only loop you need this semester

Branch → commit → pull request → merge

Start from current main
git checkout main
git pull
git checkout -b feature/12-student-card
Why

A branch is a private workspace. Nothing you do on it can break what your group is running, so you can commit half-finished work without apologising for it.

Name it after the issue it closes. feature/12-… means issue 12 — future you will thank present you.

Commit as you go
git add src/components/StudentCard.tsx
git commit -m "feat(student-card): add loading and empty states"

This project uses Conventional Commits: a type, an optional scope, then what changed. Required in the Final Activity Project.

The shape
type(scope): what changed

feat(auth): add SessionContext and route guard
fix(checklist): correct unit total on repeated subjects
docs(contract): document the 409 response
refactor(api): extract the error normaliser
test(rsvp): cover the party-size ceiling
chore(deps): bump vite to 5.4
Send it to GitHub
git push -u origin feature/12-student-card

The -u is only needed the first time on a branch. After that, plain git push.

Push often

Work that exists only on your laptop is work your group cannot see and your laptop can lose. Pushing is the backup.

Open a pull request
  • Say what changed and why, in sentences
  • Reference the issue — Closes #12 — so merging closes it automatically
  • Request a reviewer from your group
One approval required

Someone else in the group reads the diff before it lands. This is not ceremony — it is the only moment where a second pair of eyes sees the code at all.

A pull request that changes contract/openapi.yaml needs approval from the other side of that contract. More on this in 2.3.

Merge, then clean up
git checkout main
git pull
git branch -d feature/12-student-card
Then start again

Every task is one trip round this loop. Small branches merge easily; a branch that lives for two weeks becomes a conflict you will dread.

Merge early, merge often is not a slogan — it is conflict avoidance.

A convention, not a preference

Conventional Commits

Every commit message in this course

TypeUse it whenExample

Rejected in review

update

fix bug

asdf

final na talaga

feat: changes

Accepted

feat(student-card): add loading and empty states

fix(contrast): darken disabled button label to pass AA

docs(contract): add the 429 rate-limit response

Why bother
  • The log becomes searchable. git log --oneline --grep="^feat" is every feature your group shipped.
  • Review gets faster. The type tells a reviewer what kind of scrutiny the diff needs before they open it.
  • It forces one change per commit. If you cannot pick a type, the commit is doing two things and should be two commits.
Two rules that catch most mistakes
  • Imperative mood — "add", not "added" or "adds". Read it as "this commit will… add loading states".
  • Lower case, no full stop, and keep the first line under about 70 characters. Detail goes in the body, after a blank line.

A breaking change gets a ! before the colon — feat(contract)!: rename load to subjects. You will need this in Lesson 2.3.

The only question that matters

What makes something a component?

Bad reasons to extract
  • "The file was getting long"
  • "It is about 50 lines, that feels right"
  • "Every tutorial has a Header component"
  • "It looked like a box"
Good reasons to extract
  • It appears more than once, now or obviously soon
  • It has its own states — loading, empty, error, disabled
  • It has a name your group already says out loud — "the student card", "the approval row"
  • It would be tested on its own

The strongest signal is the third one. If your group has a word for it, it is a component. Vocabulary that already exists in how people talk about the product is a boundary the design found for you.

A theme for the whole module

Props are a component's contract

The prop type is the agreement
type StudentCardProps = {
  student: { id: string; fullName: string; program: string }
  status: 'active' | 'pending' | 'inactive'
  onSelect?: (id: string) => void
}

Anyone using this component knows exactly what it needs, and TypeScript refuses to let them forget one.

This idea comes back three times in this module, at three scales:

Props
The contract between a parent and a child component.
Context value
The contract between a provider and everything beneath it.
OpenAPI
The contract between your whole frontend and your whole backend.

Same idea each time: write down the shape, then both sides can move independently.

A smell worth recognising

When a component takes eleven props

Configuration
<Card
  title showBorder padded
  variant="outlined" size="md"
  headerRight={…} footer={…}
  collapsible defaultOpen
  onToggle={…} />

Every new use adds a prop. The component becomes a small framework nobody understands, and changing it risks four screens at once.

Composition
<Card>
  <Card.Header>
    Enrolled subjects
    <Badge>18 units</Badge>
  </Card.Header>
  <Card.Body>{children}</Card.Body>
</Card>

The caller arranges the pieces. The component stays small, and a new layout needs no new prop.

Rule of thumb: a boolean prop that only ever exists to show or hide a chunk of markup is usually asking to be children instead.

Module 1's seven states, in code

Every state is a rendering decision, not an afterthought

The shape most components end up with
function SubjectList({ query }) {
  if (query.isPending) return <SubjectListSkeleton />
  if (query.isError)   return <ErrorState onRetry={query.refetch} />
  if (!query.data.length) return <EmptyState />

  return (
    <ul>{query.data.map(s => <SubjectRow key={s.id} subject={s} />)}</ul>
  )
}

Four returns, in this order, before the happy path. If a component has only the last one, it is unfinished.

The design QA still applies
  • Loading has a shape, not a spinner in the void
  • Empty says what to do next, not "No data"
  • Error says what happened and offers a retry
  • Focus is visible on everything interactive

These were graded in Module 1 against a static mockup. From now on they are graded against a screen with real, variable latency — which is harder, and the subject of Lesson 2.5.

Lesson 2.2 · LO 2.1

State that the whole
tree needs

Who is signed in? Almost every component wants to know. Passing it down by hand does not scale.

The problem, measured

Prop drilling

Passing user down by hand

Drag the depth. Every component in red takes a user prop it does not use — it only passes it along.

What that costs
  • Every intermediate component's prop type grows for no reason
  • Moving a component means re-threading the prop through a new parent
  • Adding a second piece of shared state doubles the noise
  • A component that "needs user" is now impossible to test in isolation without inventing one

Two levels of drilling is fine. Five is a signal.

The tool

Context: a value any descendant can read

Three parts, always
const SessionContext = createContext(null)

export function SessionProvider({ children }) {
  const [session, setSession] = useState(null)
  const value = useMemo(() => ({ session, setSession }), [session])
  return <SessionContext.Provider value={value}>
    {children}
  </SessionContext.Provider>
}

export function useSession() {
  const ctx = useContext(SessionContext)
  if (!ctx) throw new Error('useSession outside SessionProvider')
  return ctx
}
Why the hook, and why it throws

Nobody outside this file touches SessionContext directly. They call useSession().

The throw turns a confusing bug — session is mysteriously null — into an error message that names the actual mistake: you forgot the provider.

Why useMemo

Without it, value is a brand-new object on every render of the provider, so every consumer re-renders even when nothing changed.

The mistake everyone makes once

One context per concern — not one big one

One AppContext
{ session, theme, sidebarOpen,
  currentStudent, toasts,
  tableDensity, unreadCount }

Any change to any field re-renders every consumer. Toggle the sidebar and the whole app re-renders, including a 200-row table.

It also becomes a dumping ground: nobody can say what belongs in it, so everything does.

Narrow contexts
SessionContext      → session, profile, role
AdviseeContext      → the record being worked on
PreferencesContext  → theme, density

Changing the theme re-renders what reads the theme. Nothing else notices.

Each one has an obvious answer to "does this belong here?"

Your Final Activity Project specification already names the contexts your system needs — they are in §8 State Management. That list was written to be small on purpose.

When useState stops fitting

Ordered transitions want a reducer

Four independent booleans
const [loading, setLoading] = useState(false)
const [error, setError]     = useState(null)
const [data, setData]       = useState(null)
const [retrying, setRetrying] = useState(false)

Nothing stops loading && error && data all being truthy at once. That state is meaningless, but it is representable — so eventually it happens, and the UI renders something nobody designed.

One state machine
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success', data: Subject[] }
  | { status: 'error', message: string }

Impossible combinations cannot be written down. The component switches on status and every branch is a state somebody designed.

The rule: independent toggles → useState. A sequence with rules about what follows what → useReducer. Scanning at a check-in desk (idle → scanning → resolving → accepted / duplicate / rejected) is the second kind.

Guarding routes — and what that is worth

A route guard is a redirect, not a lock

The guard
function RequireRole({ role, children }) {
  const { session, profile, status } = useSession()
  if (status === 'loading') return <FullPageSkeleton />
  if (!session) return <Navigate to="/login" replace />
  if (profile.role !== role) return <Navigate to="/" replace />
  return children
}

Note the loading branch. Without it the guard bounces a signed-in user to /login for a moment on every refresh, while the session is still resolving.

Say this out loud

This code runs on the user's machine, in a bundle they can read and modify. Anyone can delete the check with devtools.

It stops an honest user from landing on a screen that would be broken or confusing for them. It stops an attacker from nothing at all.

The real enforcement is Row Level Security in the database — Module 4, lesson 4.4. Until then, hold both ideas at once: guards are for usability, the server is for security.

Lesson 2.3 · the spine of the semester

Agree the shape
before either side builds

Your backend does not exist yet. It is five weeks away. You are going to build against it anyway.

What this lesson prevents

Integration day, without a contract

Week 13, 11pm
  • Frontend expects studentId. Backend sends student_id.
  • Frontend expects units as a number. It arrives as "18".
  • Frontend renders subjects[]. Backend returns { data: { subjects: [] } }.
  • Nobody knows what a failed enrollment returns, because nobody ever decided.
  • Both halves are "done". Neither works.
Why it happens

Two people built from the same conversation and remembered it differently. Nothing was written down that either could be wrong against.

The fix is not "communicate better"

It is to write the shapes down in a file, in a format both sides can check mechanically, before either side starts.

This is not hypothetical for you. Your backend is Module 4 and your integration is Module 5. The gap between them is real and it is seven weeks wide.

Definition

A contract is every shape, agreed and written down

For each operation
What goes in

Path, method, parameters, request body — with types, and which fields are required.

For each operation
What comes back

Every status code, and the body shape for each one. Including the failures.

For the whole API
Shared shapes

Reusable schemas — a Student is a Student everywhere, defined once.

The part people skip

The error responses. Almost every team specifies the happy path and leaves failures to be discovered. But the failures are what your UI spends most of its code handling — and "what does a 409 look like" is exactly the question you cannot answer at 11pm on integration day.

The format

OpenAPI, in three minutes

enrollment-api.yaml
openapi: 3.1.0
info: { title: Enrollment API, version: 1.0.0 }

paths:
  /students/{id}/load:
    get:
      operationId: getStudentLoad
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Load'
        '404':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'

components:
  schemas:
    Load:
      type: object
      required: [studentId, totalUnits, subjects]
      properties:
        studentId:  { type: string }
        totalUnits: { type: integer }
        subjects:
          type: array
          items: { $ref: '#/components/schemas/Subject' }
Four things to find
paths
Every URL, and the methods it supports.
operationId
A stable name for the operation. This becomes the method name in your generated client — and your Query key.
responses
Keyed by status code. Every code your UI must handle.
components.schemas
Shapes defined once and referenced with $ref.

YAML is indentation-sensitive and unforgiving. Run redocly lint before you commit — it catches the mistakes that would otherwise show up as a confusing generated type.

Two ways round

Contract-first vs code-first

Code-first

Build the backend, then generate documentation from what you built.

The spec describes whatever happened. If the backend named a field badly, the spec faithfully documents the bad name.

The frontend cannot start until the backend exists. One person waits.

Fine for a solo project where you are both halves.

Contract-first

Agree the spec, then both halves build to it.

The spec is a decision, reviewed before it is expensive to change.

Both halves start on day one. The frontend runs against a mock.

Necessary the moment more than one person is involved — which is your situation.

This is the whole reason the contract is a group deliverable in Activity 4, and why a pull request touching it needs approval from the other side.

Interactive · generated types

Types are generated, never hand-written

Toggle a field and watch the TypeScript change openapi-typescript
Why not just write the interface?

Because a hand-written mirror of the server drifts, and drifts silently. The backend makes a field nullable; your interface still says it is a string; TypeScript still compiles; the app crashes at runtime on the one record where it is null.

The command
npx openapi-typescript contract/openapi.yaml \
  -o contract/generated/schema.d.ts

Commit the output. CI re-runs it and fails if what you committed is stale — so the generated file can never quietly disagree with the spec.

A pattern worth naming now

One source of truth, and everything else downstream

        ↓ openapi-typescript
contract/generated/       ← derived, never edited
Module 4 · week 10
supabase/migrations/      ← the truth
        ↓ supabase gen types
src/lib/supabase/…types  ← derived, never edited

Same shape, different subject. When you meet the Module 4 command in seven weeks, it should feel like recognition rather than a new topic — and the same rule will apply: if a file says "generated", editing it by hand is always a mistake.

Lesson 2.4 · LO 2.1

One way in,
one way out

Every request through one wrapper. Every fetched thing in one cache.

Built against the spec, not invented

The typed client

src/lib/api/client.ts
import createClient from 'openapi-fetch'
import type { paths } from '../../../contract/generated/schema'

export const api = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_BASE_URL,
})

api.use({
  onRequest({ request }) {
    const token = getAccessToken()
    if (token) request.headers.set('Authorization', `Bearer ${token}`)
    return request
  },
  onResponse({ response }) {
    if (response.status === 401) redirectToLogin()
    return response
  },
})

The <paths> generic is the whole trick: it is the generated type, so calling an endpoint that is not in the spec will not compile.

What belongs in the interceptor
  • Attaching the auth token
  • Normalising errors into one shape
  • Handling 401 globally
  • The base URL — the one line you change in Module 5
What does not
  • Business rules
  • Anything screen-specific
  • Silent retries that hide a real failure
The idea this lesson exists for

Server data is not component state

Treating it as component state
const [subjects, setSubjects] = useState([])
useEffect(() => {
  api.GET('/students/{id}/load', …)
     .then(r => setSubjects(r.data.subjects))
}, [id])
  • No loading state until you add a second useState
  • No error state until you add a third
  • Two screens showing the same data fetch it twice
  • After a mutation, nothing knows to refetch
  • Race condition: change id twice quickly and the wrong response can win
Treating it as a cache
const load = useQuery({
  queryKey: ['getStudentLoad', id],
  queryFn: () => api.GET('/students/{id}/load', …),
})
  • isPending, isError, data — all of them, free
  • Two screens, same key, one request
  • Invalidate the key after a mutation and everything refetches
  • Out-of-order responses handled for you

The mental shift: that data lives on a server. What you hold is a copy, and copies go stale. Every problem in the left column comes from pretending otherwise.

The approval queueQueryServer-owned, and shared — another organiser may be approving right now.
Whether a modal is openuseStateOne component's concern. It does not cross the tree, so it does not need Context.

The failure to avoid: fetching with Query and then copying the result into Context "so other components can see it". Now you have two copies and you are hand-syncing them. If two components need the same server data, they use the same query key — that is what the cache is for.

Loading, done properly

A skeleton is the shape of what is coming

Centred spinner

Says "something is happening" and nothing else.

When data lands, the whole layout appears at once and everything below it jumps.

Gives the eye nowhere to rest, so the wait feels longer than it is.

Skeleton

Occupies the same space the content will, so nothing moves when it arrives.

Communicates structure before content — the user starts reading the layout early.

Measurably shortens perceived wait, at the cost of building it once.

Build the skeleton from the real component. If they drift apart, the layout jumps again and you have the worst of both. Reusing the component's own spacing and sizes is the reliable way to keep them honest.

The two states that get defaulted

Empty and error are designed, not printed

Empty — three kinds, three answers
Nothing yet
"No reviews yet. Be the first to add one." — plus the button that does it. This is an opportunity, not an apology.
Nothing matched
"No students match maria in Computer Science." — echo the filters, and offer to clear them.
Nothing permitted
Say the account cannot see this and who to contact. Never an empty table that looks broken.
Error — what went wrong, and what now
  • "Something went wrong"
  • "Error: undefined"
  • A raw stack trace
  • A dead end with no way forward
  • "Could not load your subjects. Check your connection." + Retry
  • "You are signed out." + Sign in
  • "Too many requests — try again in a minute." (your 429, from the spec)

Every one of these is a documented response in your contract. The spec tells you which errors your UI must be able to render.

LO 2.2 · cross-device

Mobile-first is a default, not a media query

Tailwind breakpoints are min-width
<div class="grid grid-cols-1
            md:grid-cols-2
            lg:grid-cols-3 gap-4">

Unprefixed classes are the phone. Prefixed ones add capability as the screen grows. Writing it the other way round means fighting your own CSS at every breakpoint.

The table problem

A 7-column table cannot shrink to 320px. Your options, in order of preference: collapse each row into a card below md; or let the table scroll inside its own container — never the page body.

The floor, and how to check it
  • 320px with no horizontal scroll on the body
  • 200% zoom still usable — this is the same problem as a small screen, and it is a WCAG requirement
  • Tap targets 44px or larger
  • Nothing important hidden behind hover — there is no hover on a phone

Two of the systems in your project are used on a phone, standing up — a guest checking an RSVP, staff scanning at a door. For those, mobile is not the fallback case. It is the real one.
