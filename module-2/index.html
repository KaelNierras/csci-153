What happens without it

Zipping folders

Two people edit one file. Somebody's afternoon disappears, and nobody notices until the demo.

No answer to "when did this break?"

Who wrote what is a matter of memory.

One repository

Every change is dated, attributed, and reversible.

Different files never collide. The same file is detected, not silently lost.

git log answers "when did this break" in seconds.

Contribution is evidence, not recollection.

This is why every member needs commits. The history is the only durable record of who did what.

The only loop you need this semester

Branch → commit → pull request → merge

Start from current main
git checkout main
git pull
git checkout -b feature/12-student-card
Why

A branch is a private workspace. Nothing you do there can break what your group is running — so commit half-finished work freely.

Name it after the issue it closes: feature/12-… is issue 12.

Commit as you go
git add src/components/StudentCard.tsx
git commit -m "feat(student-card): add loading and empty states"

Conventional Commits: a type, an optional scope, then what changed. Required in the Final Activity Project.

The shape
type(scope): what changed

feat(auth): add SessionContext and route guard
fix(checklist): correct unit total on repeated subjects
docs(contract): document the 409 response
refactor(api): extract the error normaliser
test(rsvp): cover the party-size ceiling
chore(deps): bump vite to 5.4
Send it to GitHub
git push -u origin feature/12-student-card

-u only the first time on a branch. After that, plain git push.

Push often

Work only on your laptop is work your group cannot see — and your laptop can lose it.

Open a pull request
  • Say what changed and why
  • Closes #12 — merging then closes the issue
  • Request a reviewer from your group
One approval required

Someone else reads the diff before it lands. That is the only moment a second pair of eyes sees the code.

A PR touching contract/openapi.yaml needs approval from the other side of that contract — see 2.3.

Merge, then clean up
git checkout main
git pull
git branch -d feature/12-student-card
Then start again

One task, one trip round this loop. Small branches merge easily; a two-week branch becomes a conflict.

Merge early, merge often is conflict avoidance, not a slogan.

Why bother
  • The log becomes searchable. git log --oneline --grep="^feat" is every feature you shipped.
  • Review gets faster. The type says what kind of diff it is before anyone opens it.
  • One change per commit. Cannot pick a type? It should be two commits.
Two rules that catch most mistakes
  • Imperative mood — "add", not "added". Read it as "this commit will… add loading states".
  • Lower case, no full stop, first line under 70 characters. Detail goes in the body.

A breaking change gets a ! before the colon — feat(contract)!: rename load to subjects. Needed in 2.3.

The only question that matters

What makes something a component?

Bad reasons to extract
  • "The file was getting long"
  • "It is about 50 lines, that feels right"
  • "Every tutorial has a Header component"
  • "It looked like a box"
Good reasons to extract
  • It appears more than once, now or obviously soon
  • It has its own states — loading, empty, error, disabled
  • Your group already says its name out loud — "the student card", "the approval row"
  • It would be tested on its own

The third is the strongest signal. If your group has a word for it, it is a component — the vocabulary found the boundary for you.

A theme for the whole module

Props are a component's contract

The prop type is the agreement

  student: { id: string; fullName: string; program: string }
  status: 'active' | 'pending' | 'inactive'
  onSelect?: (id: string) => void

Anyone using it knows exactly what it needs, and TypeScript will not let them forget one.

The same idea, at three scales:

Props
The contract between a parent and a child component.
Context value
The contract between a provider and everything beneath it.
OpenAPI

The shape most components end up with

The problem, measured

Prop drilling

Passing user down by hand

Drag the depth. Everything in red takes a user prop it never uses.

What that costs
  • Every prop type in between grows for no reason
  • Moving a component means re-threading the prop
  • A second piece of shared state doubles the noise
  • Testing any of them in isolation means inventing a user

Two levels of drilling is fine. Five is a signal.

The tool

Context: a value any descendant can read

Three parts, always
const SessionContext = createContext(null)

export function SessionProvider({ children }) {
  const [session, setSession] = useState(null)
  const value = useMemo(() => ({ session, setSession }), [session])
  return <SessionContext.Provider value={value}>
    {children}
  </SessionContext.Provider>
}

export function useSession() {
  const ctx = useContext(SessionContext)
  if (!ctx) throw new Error('useSession outside SessionProvider')
  return ctx
}
Why the hook, and why it throws

Nobody outside this file touches SessionContext — they call useSession().

The throw turns a confusing bug (session is mysteriously null) into a message that names the mistake: you forgot the provider.

Why useMemo

Without it, value is a new object every render — so every consumer re-renders for nothing.

The mistake everyone makes once

One context per concern — not one big one

One AppContext
{ session, theme, sidebarOpen,
  currentStudent, toasts,
  tableDensity, unreadCount }

Any field changing re-renders every consumer. Toggle the sidebar, re-render the 200-row table.

And it becomes a dumping ground — nobody can say what belongs in it.

Narrow contexts
SessionContext      → session, profile, role
AdviseeContext      → the record being worked on
PreferencesContext  → theme, density

Changing the theme re-renders what reads the theme. Nothing else notices.

Each has an obvious answer to "does this belong here?"

Your project spec already names the contexts your system needs, in §8 State Management. That list is short on purpose.

When useState stops fitting

Ordered transitions want a reducer

Four independent booleans
const [loading, setLoading] = useState(false)
const [error, setError]     = useState(null)
const [data, setData]       = useState(null)
const [retrying, setRetrying] = useState(false)

Nothing stops loading && error && data all being true at once. Meaningless, but representable — so it eventually happens, and the UI renders something nobody designed.

One state machine
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success', data: Subject[] }
  | { status: 'error', message: string }

Impossible combinations cannot be written down. Switch on status and every branch is designed.

The rule: independent toggles → useState. A sequence with rules about what follows what → useReducer. Door scanning (idle → scanning → resolving → accepted / duplicate / rejected) is the second kind.

Guarding routes — and what that is worth

A route guard is a redirect, not a lock

The guard
function RequireRole({ role, children }) {
  const { session, profile, status } = useSession()
  if (status === 'loading') return <FullPageSkeleton />
  if (!session) return <Navigate to="/login" replace />
  if (profile.role !== role) return <Navigate to="/" replace />
  return children
}

Note the loading branch. Without it, every refresh flashes a signed-in user to /login while the session resolves.

Say this out loud

This runs on the user's machine, in a bundle they can read and edit. Devtools deletes the check.

It keeps an honest user off a screen that would confuse them. It stops an attacker from nothing.

Real enforcement is Row Level Security in the database (Module 4.4). Guards are for usability; the server is for security.

Lesson 2.3 · the spine of the semester

Agree the shape
before either side builds

Your backend does not exist yet. You are going to build against it anyway.

What this lesson prevents

Integration day, without a contract

Week 13, 11pm
  • Frontend expects studentId. Backend sends student_id.
  • Frontend expects units as a number. It arrives as "18".
  • Frontend renders subjects[]. Backend returns { data: { subjects: [] } }.
  • Nobody decided what a failed enrollment returns.
  • Both halves are "done". Neither works.
Why it happens

Two people built from one conversation and remembered it differently. Nothing was written down to be wrong against.

The fix is not "communicate better"

Write the shapes in a file both sides can check, before either side starts.

Not hypothetical: your backend is Module 4, and you implement it in sprint 1. That gap is six weeks wide.

Definition

A contract is every shape, agreed and written down

For each operation
What goes in

Path, method, parameters, request body — typed, and which fields are required.

For each operation
What comes back

Every status code and its body shape. Including the failures.

For the whole API
Shared shapes

Reusable schemas — a Student is a Student everywhere, defined once.

The part people skip

The error responses. Teams specify the happy path and discover the failures later — but failures are most of your UI code, and "what does a 409 look like" is the question you cannot answer at 11pm.

The format

OpenAPI, in three minutes

enrollment-api.yaml
openapi: 3.1.0
info: { title: Enrollment API, version: 1.0.0 }

paths:
  /students/{id}/load:
    get:
      operationId: getStudentLoad
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Load'
        '404':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'

components:
  schemas:
    Load:
      type: object
      required: [studentId, totalUnits, subjects]
      properties:
        studentId:  { type: string }
        totalUnits: { type: integer }
        subjects:
          type: array
          items: { $ref: '#/components/schemas/Subject' }
Four things to find
paths
Every URL, and the methods it supports.
operationId
A stable name. It becomes your generated method name — and your Query key.
responses
Keyed by status code. Every code your UI must handle.
components.schemas
Shapes defined once and referenced with $ref.

YAML is indentation-sensitive and unforgiving. Run redocly lint before you commit.

Two ways round

Contract-first vs code-first

Code-first

Build the backend, then generate docs from what you built.

The spec describes whatever happened — bad field names included.

The frontend waits for the backend.

Fine solo.

Contract-first

Agree the spec, then both halves build to it.

The spec is a decision, reviewed while it is still cheap to change.

Both halves start on day one; the frontend runs on a mock.

Necessary as soon as two people are involved — your situation.

This is why the contract is a group deliverable in Activity 4, and why a PR touching it needs the other side's approval.

Interactive · generated types

Types are generated, never hand-written

Toggle a field and watch the TypeScript change openapi-typescript
Why not just write the interface?

A hand-written mirror drifts silently. The backend makes a field nullable, your interface still says string, TypeScript still compiles — and the app crashes on the one null record.

The command
npx openapi-typescript contract/openapi.yaml \
  -o contract/generated/schema.d.ts

Commit the output. CI re-runs it and fails if yours is stale, so it can never quietly disagree with the spec.

A pattern worth naming now

One source of truth, and everything else downstream

Lesson 2.4 · LO 2.1

One way in,
one way out

Every request through one wrapper. Every fetched thing in one cache.

Built against the spec, not invented

The typed client

src/lib/api/client.ts
import createClient from 'openapi-fetch'
import type { paths } from '../../../contract/generated/schema'

export const api = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_BASE_URL,
})

api.use({
  onRequest({ request }) {
    const token = getAccessToken()
    if (token) request.headers.set('Authorization', `Bearer ${token}`)
    return request
  },
  onResponse({ response }) {
    if (response.status === 401) redirectToLogin()
    return response
  },
})

The <paths> generic is the trick: it is the generated type, so an endpoint that is not in the spec will not compile.

What belongs in the interceptor
  • Attaching the auth token
  • Normalising errors into one shape
  • Handling 401 globally
  • The base URL — the one line you change in Module 5
What does not
  • Business rules
  • Anything screen-specific
  • Silent retries that hide a real failure
The idea this lesson exists for

Server data is not component state

Treating it as component state
const [subjects, setSubjects] = useState([])
useEffect(() => {
  api.GET('/students/{id}/load', …)
     .then(r => setSubjects(r.data.subjects))
}, [id])
  • Loading state costs a second useState; error a third
  • Two screens on the same data fetch it twice
  • After a mutation, nothing knows to refetch
  • Change id twice quickly and the wrong response can win
Treating it as a cache
const load = useQuery({
  queryKey: ['getStudentLoad', id],
  queryFn: () => api.GET('/students/{id}/load', …),
})
  • isPending, isError, data — free
  • Two screens, same key, one request
  • Invalidate the key; everything refetches
  • Out-of-order responses handled for you

The shift: the data lives on a server. You hold a copy, and copies go stale. Every problem on the left comes from pretending otherwise.

Interactive · cache and invalidation

Keys come from the contract

The cache, live run a mutation and watch what goes stale

Key = operationId + parameters. Then invalidation is something you look up rather than remember — the practical reason the contract has stable operation names.

The decision that keeps both clean

Which tier does this state belong to?

The stateWhere it goesWhy
The signed-in session and roleContextClient-owned, needed everywhere, changes rarely.
A student's enrolled subjectsQueryServer-owned — it changes without you, so it must be refetchable.
Which advisee is being viewedContextAn id the client chose. The record it points at is a Query.
Theme and table densityContextClient-owned preference, persisted locally.

Whether a modal is openuseStateOne component's concern. It never crosses the tree.

The failure to avoid: fetching with Query, then copying the result into Context "so others can see it" — now you hand-sync two copies. Two components needing the same server data use the same query key.

Centred spinner

The two states that get defaulted

Empty and error are designed, not printed

Empty — three kinds, three answers
Nothing yet
"No reviews yet. Be the first." — plus the button. An opportunity, not an apology.
Nothing matched
"No students match maria in Computer Science." — echo the filters, offer to clear.
Nothing permitted
Say the account cannot see this, and who to ask. Never a table that looks broken.
Error — what went wrong, and what now
  • "Something went wrong"
  • "Error: undefined"
  • A raw stack trace
  • A dead end with no way forward
  • "Could not load your subjects." + Retry
  • "You are signed out." + Sign in
  • "Too many requests — try again in a minute." (the 429)

Each one is a documented response in your contract. The spec lists the errors your UI must render.

LO 2.2 · cross-device

Mobile-first is a default, not a media query

Tailwind breakpoints are min-width
<div class="grid grid-cols-1
            md:grid-cols-2
            lg:grid-cols-3 gap-4">

Unprefixed = the phone. Prefixed classes add capability as the screen grows.

The table problem

A 7-column table cannot shrink to 320px. Best: collapse each row into a card below md. Otherwise scroll it inside its own container — never the page body.

The floor, and how to check it
  • 320px with no horizontal scroll on the body
