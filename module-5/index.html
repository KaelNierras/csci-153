Lesson 5.1 · week 14 clinic · 45 minutes

One test that
proves the app works

A real browser, a real backend, a real flow.

Taught in the week you apply it
What this adds to Lesson 2.7

Different question, different cost

A unit test asks…

"Does canAddSubject reject a 24-unit load?"

Milliseconds. No browser, no server, no database. You run hundreds without noticing.

It cannot tell you the button was wired to the wrong handler.

An e2e test asks…

"Can a student sign in, add three subjects, submit, and see the confirmation?"

Tens of seconds. Real browser, real requests, real rows. You keep a handful.

It is the only kind that proves the app works.

Both, in that ratio. Many cheap tests on the rules, a few expensive ones on the journeys that must never break — sign in, the core flow, and one permission boundary.

The one to write first

The flow your project exists to do

e2e/enrollment.spec.ts
test('a student submits an enrollment', async ({ page }) => {
  await loginAs(page, 'student')          // a real session

  await page.goto('/subjects')
  await page.getByRole('searchbox').fill('CSci')
  await page.getByRole('button', { name: 'Add' }).first().click()

  await page.goto('/enrollment')
  await expect(page.getByText('3 units')).toBeVisible()

  await page.getByRole('button', { name: 'Submit' }).click()
  await expect(page.getByText('Waiting for your adviser')).toBeVisible()
})

getByRole, not a CSS class. A test that breaks when you restyle a button was testing the wrong thing.

The rule that makes e2e worth doing

Run as an authenticated role. A test using the service role bypasses RLS — so it passes while your app is broken for every real user, which is worse than having no test.

And one test for the boundary
test('a student cannot open the adviser queue',
  async ({ page }) => {
    await loginAs(page, 'student')
    await page.goto('/advising')
    await expect(page).toHaveURL('/')
  })
Lesson 5.2 · week 14 clinic

A test nobody
asked for proves
nothing either

Where test cases come from, and why you do not write your own.

The workflow your spec's §12 requires

Whoever writes the case does not write the test

01 · Project Manager
Files the case as an issue

Scenario, steps, expected result. In words, from the user's side. No code.

02 · A contributor
Writes the Playwright test

On a branch, in a PR that says Closes #47. Merging closes the issue.

03 · Everyone
CI runs it forever

The case stops being a document somebody remembers and becomes a check that cannot be skipped.

Why the split is deliberate

Someone writing both tends to write the test they know passes. Handing the case to a different person surfaces the ambiguity in the description — and an ambiguous test case is a requirement nobody actually agreed on.

This is graded. Activity 10 is test cases you did not write, implemented as tests that pass.

What the Project Manager actually writes

Two cases for the same rule. Only one can be implemented.

Not implementable
#41 · Unit ceiling should work

The system should stop students from
enrolling in too many units.

Too many is how many? Stopped where — the button, the request, the database? What does the student see? Three people will write three different tests, and all of them can claim to pass.

Implementable
#41 · A student cannot exceed 21 units

Given  Maria has a draft at 18 units
When   she adds CSci 153 (6 units)
Then   the Add button is disabled, and
       the row says "would put you at 24,
       the limit is 21"
And    posting it with a REST client
       returns 422 UNIT_CEILING

Given / When / Then, in the user's words, with the observable result named. The last line is what makes it a real case rather than a UI check.

Write the case from the specification, not from the screen. A case written by looking at what the app currently does can only ever confirm what it currently does.

When a case fails, or a DITL run trips

A bug report nobody can reproduce is a complaint

Five lines, every time
Steps
Numbered, from signed out. Including which account.
Expected
What the spec or the contract says should happen.
Actual
What happened, with the exact message or status code.
Where
Staging or local, which browser, what time — so the logs can be found.
Severity
Blocks the cycle, or does not. Only the first kind stops a release.
Triage, in sprint 4
  • Blocker — the DITL run cannot continue. Fix now
  • Major — a role cannot finish its job another way. Fix this sprint
  • Minor — wrong but survivable. Fix if the blockers are clear
  • Won't fix — say so in the issue, with the reason

"Won't fix" is a legitimate engineering answer and an unanswered issue is not. Closing an issue with a reason is evidence of judgement; letting it rot is evidence of neither.

Lesson 5.3 · week 16

Every test passes.
Does the system
actually work?

One full cycle, every role, in order, on the deployed app.

The gap your test suite cannot see

A green suite is not a working system

What your tests check
  • Each function, in isolation — unit
  • Each flow, on its own, from a clean state — end to end

Every one of them starts from a database you reset and a user you just created. That is what makes them repeatable, and it is also what makes them blind.

What only a Day In The Life run catches
  • State the previous step left behind
  • Two roles acting on the same record, in sequence
  • A screen nobody thought to open second
  • The step that works but takes four minutes
  • The email, the notification, the thing outside the app

Day In The Life testing is one complete operational cycle, walked end to end, in the order a real day happens — not feature by feature. It is the last check before a system is accepted, and it is the one that finds the things nobody wrote a case for.

Interactive · one cycle, six moves

Write the day down before you walk it

Who, and what they do

Nobody. The term is already open and the subjects are seeded. Start from data that has a history, not an empty database.

What this step catches

Seed data that only works once. If your app needs a fresh reset to behave, say so now — because the real one will not get one.

Who, and what they do

Maria, student. Signs in, searches the catalog, adds subjects until she is near the ceiling, leaves the page, comes back.

What this step catches

The draft that did not persist. The unit meter that disagrees with the server after a reload. The search that forgets its filter.

Who, and what they do

Maria submits. Then tries to edit the enrollment she has just submitted.

What this step catches

The screen that still offers Add after submission. R5 enforced in the database but not reflected in the UI, so the button 409s instead of being absent.

Who, and what they do

Ramon, adviser. Opens his queue, finds Maria, returns it with a reason.

What this step catches

The handover. Does Maria's screen tell her she was returned, and does it show Ramon's reason in his words? This is the step feature tests always skip.

Who, and what they do

Maria reads the reason, drops a subject, adds another, resubmits.

What this step catches

The second lap. Most bugs live here — the state machine that only ever ran forwards, the rollup that double-counted, the reason that stayed on screen after it was addressed.

Who, and what they do

Ramon approves. Maria refreshes. Both look at the same enrollment.

What this step catches

Two people, one record, two different answers. Stale caches, an unrevalidated query key, a status shown from the client's memory rather than the server's.

Your system is not enrollment. Write your own six steps — one cycle of the thing your spec exists to do, with a named person at every step.

The rules that make it worth doing

Four conditions, and none of them are optional

On the deployed app

Staging, at its real URL, with the real database behind it. Not localhost, not the mock. Half of what a DITL run finds is environment, not code.

Driven by someone outside the group

Another group, or me. You may not touch the keyboard and you may not explain. Every sentence you want to say out loud is a defect in the interface.

From data with a history

Not a fresh reset. A database that has been used, with rows from earlier steps still in it — which is the state every real system is permanently in.

Nothing is fixed during the run

You write it down and keep walking. Stopping to patch turns a measurement into a debugging session and you lose the rest of the cycle.

One person scribes. Every hesitation, every wrong turn, every "wait, where is it" — those are findings even when nothing is broken. A user who cannot find the button has met a defect.

A run that produces nothing was not a run

Every finding becomes one of three things

It is broken
A bug issue

Steps, expected, actual, and which DITL step it surfaced in. Fixed in sprint 4, and the fix closes the issue.

It works, but nobody could find it
A UX issue

The 12-point QA is where it gets settled. "The user was confused" is a finding, not an excuse.

It broke and nothing caught it
A missing test case

File the case, implement the Playwright test, and it can never regress silently again. This is how the suite grows honestly.

The gate for this module

A DITL run completes across every role on the deployed app, driven by someone outside the group, with every finding filed — and the run is repeated until it completes without a blocking defect. That repetition is the point: the first run always fails, and the second one is the one that means something.

This is also your Final Web Project demonstration, rehearsed. The demo is a Day In The Life run with an audience — so if the run is clean, the demo is already written.

Weeks 16–17 · 20% of the course

Somebody reads
your repository

And asks you about it. Out loud.

The 20% nobody prepares for

What gets opened, and what it shows

The files
  • git log — did everyone contribute, weekly, with messages that say what changed?
  • contract/openapi.yaml — and whether the implementation still matches it
  • Migrations — do they replay from empty, and is every schema change in one?
  • Policies — is RLS on every table, with with check on updates?
  • A component of our choosing — its states, its props, its tokens
The questions
  • "Why is this a component?"
  • "Where does this rule get enforced, and what happens if I post around your form?"
  • "Show me this screen's error state."
  • "Who wrote this, and what were the alternatives?"
  • "This is generated — what regenerates it?"

Individual answers, on group work. This is where individual contribution becomes visible.

You cannot revise for this in week 16. It reads fourteen weeks of habits — which is why the commit convention, the QA checklist, and "never edit a generated file" have been graded since week 3.
