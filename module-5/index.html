Lesson 5.1 · LO 5.1

Both layers,
for different reasons

Not redundancy. Two jobs that happen to look alike.

The distinction that makes the duplication sane

One is kindness. One is enforcement.

Client · a user-experience affordance

Tells the user what is wrong while they are still looking at the field, before a round trip.

  • Instant, and specific to the input
  • Saves a request that was going to fail
  • Runs on a machine the user controls

Zod plus React Hook Form, in Enroll.

Server · the actual rule

Decides what is allowed to exist, no matter who is asking or what they are asking with.

  • Constraints, triggers and policies, from Module 4
  • Applies to your app, a REST client, and a script
  • Runs somewhere the user cannot reach

The only one of the two that is load-bearing.

You have met this shape twice already: a route guard is not RLS, and units.ts is not the trigger. Same principle, third time — the client copy is a courtesy, the server copy is the truth.

Interactive · post around the form

Which layer actually stops it

A bad enrollment, sent four ways pick a path and a bad value

Run this in class with a REST client. Every rule that only lives in the form is demonstrably not a rule — and the ones that survive are the ones you can defend.

The client half, written once

A schema, not a pile of if-statements

The shape, and the messages, together
const returnSchema = z.object({
  reason: z.string()
    .trim()
    .min(10, 'Say what needs changing — at least 10 characters.')
    .max(500, 'Keep it under 500 characters.')
})

type ReturnForm = z.infer<typeof returnSchema>

z.infer gives you the TypeScript type from the schema, so the form's type and its validation cannot disagree.

Where the numbers come from

The min(10) is not invented here. It is R9 in your project context and minLength: 10 in the contract — the same rule, written in three places on purpose, each doing a different job.

The error message is part of the design. "Invalid input" tells the user nothing. Write the message you would want if you were stuck on that field at 11pm.

When the server rejects it anyway

A server error has to land on a field

The lazy version
catch (e) {
  toast.error('Something went wrong')
}

The user has a form in front of them, a specific problem, and a message that helps nobody. They will try again identically.

Using the contract's error code
if (err.body.code === 'UNIT_CEILING') {
  setError('subjectId', {
    message: err.body.message   // already user-facing
  })
}

The message lands on the control that caused it. This is why the contract has a machine-readable code as well as a human message.

Every documented response in your contract needs a place to appear in the UI. That is point 9 of the 12-point QA, and this is the lesson where it gets paid for.

Lesson 5.2 · LO 5.2

The payoff,
or the bill

Whichever it turns out to be, week 5 decided it.

.env
Do this live, and time it

The whole integration

.env — before, and after
# weeks 3 – 12: the mock, served from the contract
VITE_API_BASE_URL=http://localhost:4010

# from sprint 2: your own backend
VITE_API_BASE_URL=https://xyz.supabase.co/rest/v1

One variable. No component changes, no query changes, no type changes — because every one of those was written against the contract, not against the mock.

Why nothing else moves
  • The types came from the contract, and the contract has not changed
  • The client's base URL was always one line in one file
  • Query keys are operation names, not URLs
  • Error handling was written against documented responses

Keep both .env files. Being able to flip between mock and real in front of the class is worth more than the ten seconds it takes.

Realistically, it will not be seamless

Two kinds of break, and both are findable

A contract violation

The backend did not implement what was agreed. Field named differently, a documented status never returned, a nullable field that is never null.

Whose bug: the backend's. The fix: make the implementation match the document.

A contract error

What was agreed turned out to be wrong. The shape cannot be produced from the schema, or it is missing something the UI genuinely needs.

Whose bug: the group's, in week 5. The fix: version the contract, tell both sides, regenerate.

This is the argument for contract-first, made concrete instead of asserted. Without the document, integration failures are "it does not work" and you bisect two codebases at once. With it, every failure is one of two specific, named things.

The two that surprise everyone

Problems the mock could not have

CORS
Access to fetch at 'https://xyz.supabase.co/…'
from origin 'http://localhost:5173' has been
blocked by CORS policy

The browser refuses a cross-origin response the server did not explicitly permit. Your local Prism allowed everything; a real host does not.

Fixed on the server, by allowing your origins. Never by "disabling CORS" in the browser — that only hides it on your machine.

A real token, for the first time
// weeks 3 – 12
'mock-token-student'

// now
eyJhbGciOiJIUzI1NiIsInR5cCI6…

The mock accepted any token. Supabase verifies a signature, checks expiry, and puts a real user id in auth.uid() — which is what makes every policy you wrote start applying.

A 401 you have never seen before usually means an expired session, not broken code.

Both of these are expected, and both are twenty-minute problems if you know their names. Losing an afternoon to CORS is what happens when you do not.

Clinic 5.3 · week 12 · 45 minutes

One test that
proves the app works

A real browser, a real backend, a real flow.

Taught in the week you apply it
What this adds to Module 3.8

Different question, different cost

A unit test asks…

"Does canAddSubject reject a 24-unit load?"

Milliseconds. No browser, no server, no database. You run hundreds without noticing.

It cannot tell you the button was wired to the wrong handler.

An e2e test asks…

"Can a student sign in, add three subjects, submit, and see the confirmation?"

Tens of seconds. Real browser, real requests, real rows. You keep a handful.

It is the only kind that proves the app works.

Both, in that ratio. Many cheap tests on the rules, a few expensive ones on the journeys that must never break — sign in, the core flow, and one permission boundary.

The one to write first

The flow your project exists to do

e2e/enrollment.spec.ts
test('a student submits an enrollment', async ({ page }) => {
  await loginAs(page, 'student')          // a real session

  await page.goto('/subjects')
  await page.getByRole('searchbox').fill('CSci')
  await page.getByRole('button', { name: 'Add' }).first().click()

  await page.goto('/enrollment')
  await expect(page.getByText('3 units')).toBeVisible()

  await page.getByRole('button', { name: 'Submit' }).click()
  await expect(page.getByText('Waiting for your adviser')).toBeVisible()
})

getByRole, not a CSS class. A test that breaks when you restyle a button was testing the wrong thing.

The rule that makes e2e worth doing

Run as an authenticated role. A test using the service role bypasses RLS — so it passes while your app is broken for every real user, which is worse than having no test.

And one test for the boundary
test('a student cannot open the adviser queue',
  async ({ page }) => {
    await loginAs(page, 'student')
    await page.goto('/advising')
    await expect(page).toHaveURL('/')
  })
The workflow your spec's §12 requires

Whoever writes the case does not write the test

01 · Project Manager
Files the case as an issue

Scenario, steps, expected result. In words, from the user's side. No code.

02 · A contributor
Writes the Playwright test

On a branch, in a PR that says Closes #47. Merging closes the issue.

03 · Everyone
CI runs it forever

The case stops being a document somebody remembers and becomes a check that cannot be skipped.

Why the split is deliberate

Someone writing both tends to write the test they know passes. Handing the case to a different person surfaces the ambiguity in the description — and an ambiguous test case is a requirement nobody actually agreed on.

This is graded. Activity 10 is test cases you did not write, implemented as tests that pass.

Clinic 5.4 · week 13 · 45 minutes

The checks
you already run,
run for you

CI is automation, not a new discipline.

Taught in the week you apply it
The whole concept

Nothing here is new

What you run by hand
npm run lint
npm run typecheck
npm run test
npm run contract:check

Four commands you already have. You run them when you remember to.

.github/workflows/ci.yml
on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test
      - run: npm run contract:check

The same four. On every pull request, on a clean machine, whether anyone remembered or not.

npm ci, not npm install — it installs exactly the lockfile and fails if the lockfile disagrees with package.json. That is what makes the clean machine meaningful.

Interactive · what a red build catches

Break something and watch the gate close

Pull request #48 introduce a mistake, then run it

contract:check is the one worth having. It catches the class of bug you cannot see in a diff: generated types nobody regenerated, and an implementation that quietly stopped matching the document.

The setting that makes it real

A red build has to block the merge

Branch protection on main
  • Require a pull request — no direct pushes to main
  • Require one approval — the Module 2 rule, enforced by the platform
  • Require status checks to pass — this is the one people skip

Five minutes in repository settings, once, by whoever owns the repo.

Without that third setting

CI becomes a notification. It goes red, somebody merges anyway because the deadline is Friday, and within two weeks the build is permanently red — so nobody looks at it, and it may as well not exist.

A check nobody is forced to respect is not a check. Turn it on in week 13 and it will still be green in week 17.

Clinic 5.5 · week 15 · LO 5.3

A URL a stranger
can open

Three places, and the secrets belong in exactly one of them.

Interactive · where each piece lives

Your app is not deployed in one place

Click a piece and see what belongs there — and what must not

The frontend is static files. No server runs your React code — a CDN hands the same bundle to everyone, and the browser does the rest. That single fact explains both the VITE_ secret problem and the next slide.

The bug every group hits within an hour

It works, until someone refreshes

What happens
1 · open /            → works
2 · click to /enrollment → works
3 · press F5          → 404

Clicking never asked the server for /enrollment — the router changed the URL in the browser. Refreshing does ask, and there is no file at that path, because there is only index.html.

The fix: send everything to index.html
# Vercel · vercel.json
{ "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
] }

# Netlify · _redirects
/*  /index.html  200

Now the server hands over index.html for any path and the router works out what to show, exactly as it did when you clicked.

Test it deliberately: deploy, navigate two levels deep, refresh, and share that URL with someone else. A link a marker cannot open is a deployment that does not count.

Before you call it deployed

The list

Run this on the real URL, not localhost
The two nobody does

05 · a fresh account. Your browser has a valid session from development. A new user hits code paths you have not run in weeks.

08 · a real phone on mobile data. Not a narrow browser window — an actual device, on a connection you do not control. It is how half your users will open it.

Put the URL in your README. A deployment nobody can find is indistinguishable from no deployment.

Weeks 16–17 · 20% of the course

your repository

And asks you about it. Out loud.

The 20% nobody prepares for

What gets opened, and what it shows

The files
  • git log — did everyone contribute, weekly, with messages that say what changed?
  • contract/openapi.yaml — and whether the implementation still matches it
  • Migrations — do they replay from empty, and is every schema change in one?
  • Policies — is RLS on every table, with with check on updates?
  • A component of our choosing — its states, its props, its tokens
The questions
  • "Why is this a component?"
  • "Where does this rule get enforced, and what happens if I post around your form?"
  • "Show me this screen's error state."
  • "Who wrote this, and what were the alternatives?"
  • "This is generated — what regenerates it?"

Individual answers, on group work. This is where individual contribution becomes visible.

You cannot revise for this in week 16. It reads fourteen weeks of habits — which is why the commit convention, the QA checklist, and "never edit a generated file" have been graded since week 3.
