package.json
The distinction that organises everything

Do you call it, or does it call you?

A library — you call it

You decide when. It returns. You stay in charge of the flow.

const total = totalUnits(subjects)

openapi-fetch, date-fns, zod. Easy to remove: delete the calls.

A framework — it calls you

It owns the flow and invokes your code at moments it chooses.

function SubjectRow(props) { … }
// React decides when this runs. Not you.

react, vite, react-router. Removing one is a rewrite.

This is not trivia. It predicts how expensive a mistake is. Picking the wrong date library costs an afternoon; picking the wrong framework costs the project.

Twelve dependencies, one sentence each

Pick one what breaks if you remove it?

Where it all goes

Twelve dependencies, four hundred folders

What you asked for, and what arrived
package.json          12 things you chose
        ↓ npm install
node_modules/         ~400 folders
package-lock.json     every exact version, pinned

Your twelve have dependencies of their own, and so do those. The lockfile records the exact tree that worked, so the next person gets the same one.

Three rules
  • Commit the lockfile. It is the difference between "works on my machine" and works.
  • Never commit node_modules. It is derived, and it is enormous.
  • Never edit anything inside it. The next install erases you.

rm -rf node_modules && npm install is the answer to a surprising share of "it stopped working".

A real conflict, from this repository

Why TypeScript is pinned to 5.9

What happened, in order
$ npm create vite@latest
  → installs typescript 6.0.3

$ npm install -D openapi-typescript
npm error Could not resolve dependency:
npm error peer typescript@"^5.x" from openapi-typescript@7.13.0

openapi-typescript says: I work with TypeScript 5, and I have not been tested against 6.

Three ways out
Force it
--legacy-peer-deps. Fast, and you now own any breakage nobody has debugged.
Drop the library
Hand-write the types instead. Module 2 explained why that ends badly.
Pin TypeScript to 5.9
What Enroll does. The contract-to-types pipeline is load-bearing; being on the newest major is not.

A peer dependency is a library saying what it expects to live alongside. Ignoring it is allowed, which is exactly why it is worth understanding.

What the punctuation means

Reading a version number

MAJOR . MINOR . PATCH
vite: "^8.2.0"
       │  │  └── patch · a fix, nothing else changes
       │  └───── minor · new things, old things still work
       └──────── major · something you use has changed or gone
The prefixes
^8.2.0   any 8.x — minor and patch updates allowed
~5.9.0   any 5.9.x — patch only
 8.2.0   exactly this. Nothing moves.
Why ^ is the default, and what it costs

^ means a fresh npm install can pick up a version nobody on your team has run. Usually fine, occasionally the cause of a Tuesday you will not enjoy.

The lockfile is what makes it safe: it records what you actually installed, so ^ only moves when somebody deliberately updates.

A major bump is a reading task, not a command. Check the changelog before npm install pkg@latest, or find out from the error.

What a type buys you

Plain JavaScript
const total = enrollment.totalUnits
// or was it total_units?
// or units? or getTotal()?

You find out by running it and reading undefined. The typo is legal JavaScript, so nothing warns you.

Multiply by every field in nine operations.

TypeScript
const total = enrollment.total_units
        ~~~~~~~~~~~
Property 'total_units' does not exist.
Did you mean 'totalUnits'?

Before you run it. In the editor, while you type.

And the answer came from the contract, so it is right.

TypeScript is JavaScript plus annotations. Every file in Enroll is JavaScript with types written on it — not a different language, and it all disappears at build time.

Interactive · everything this course needs

The five, and no more

A name, a colon, a type
function totalUnits(subjects: Subject[]): number {
  return subjects.reduce((sum, s) => sum + s.units, 0)
}

const code: string = 'CSci 153'
const units: number = 3
const isFull: boolean = false
Where to write them, and where not

Always on function parameters and returns. That is the contract of the function, and it is what other people read.

Rarely on local variables. const units = 3 is already number — TypeScript infers it, and writing it again is noise that can go stale.

One of a fixed set
type EnrollmentStatus =
  | 'draft'
  | 'submitted'
  | 'approved'
  | 'returned'

// from the contract's enum. Any other string
// is now a compile error.
if (status === 'submited') // ← caught
Why this is the most useful one

A union turns a whole class of bug into a compile error: the misspelled status, the state nobody handled, the fifth case somebody added last week.

Switch on one and TypeScript will tell you which branch you forgot.

Two different absences
type Enrollment = {
  submittedAt?: string       // may not be there
  returnedReason: string | null // there, and empty
}

The contract distinguishes these, so the generated types do too.

Why the difference matters

? means the key might be missing — nobody has submitted yet, so there is no timestamp to speak of.

| null means the key is there and deliberately empty — we looked, and there is no reason because it was never returned.

Collapsing them loses the distinction between "not yet" and "no".

Both describe a shape
type SubjectRowProps = {
  subject: Subject
  onAdd?: (s: Subject) => void
}

interface SubjectRowProps {
  subject: Subject
  onAdd?: (s: Subject) => void
}
The rule for this course

Use type. It does everything interface does and also handles unions, which interface cannot.

You will see interface in other people's code and in older tutorials. It is not wrong; it is a preference. Pick one and stop thinking about it.

A type that takes a type
export const api = createClient<paths>({ … })

// createClient works with any API shape.
// <paths> tells it: this one, from our contract.

api.GET('/subjects', …)      // ✓ in the contract
api.GET('/students/all', …)  // ✗ does not compile
You will read these constantly and write them almost never

Generics are how a library says "I work with your shape, tell me what it is." useState<string>, useQuery<Enrollment>, createClient<paths> — all the same idea.

If you find yourself writing a generic in this course, stop and ask whether a plain type would do. Usually it would.

LO 3.2 · block scoping

const unless it moves

What the three actually mean
const — this name will not be reassigned
Note: the name. const subjects = [] then subjects.push(x) is legal — you changed the array, not what the name points at.
let — this name will be reassigned
A counter, an accumulator, a value built up in a loop. Rare in this codebase.
var — never
Scoped to the whole function rather than the block, which produces bugs that read as impossible. It exists for old code.
Block scope, seen
if (verdict.ok) {
  const message = 'Added'
}
console.log(message) // ✗ not defined out here

for (var i = 0; i < 3; i++) { … }
console.log(i) // 3. var leaked out of the loop.

Why const by default: a name that never changes is one less thing to track while reading. In Enroll, let appears three times in the whole src/ tree — and each one is a deliberate accumulator.

Open the file

Six hundred lines nobody wrote

contract/generated/schema.d.ts
Enrollment: {
  id: string;
  studentId: string;
  status: components["schemas"]["EnrollmentStatus"];
  totalUnits: number;
  subjects: components["schemas"]["Subject"][];
  submittedAt?: string | null;
  returnedReason?: string | null;
}

Every one of the five ideas is in this fragment. Find them.

Why this file, of all files

Nothing in it is a human's stylistic choice. Every line is a mechanical consequence of the YAML that produced it, so when you ask "why is it written this way", the answer is always because the contract says so.

Do not edit it

Regenerating overwrites you, and CI fails if what is committed has drifted. If a type is wrong, the contract is wrong — fix it there.

The whole vocabulary

  • Array — ordered slots, numbered from zero. items[0]. Order is the point.
  • Nested — an array of objects, each holding arrays. All the way down.

Interactive · the same job, four ways

Which loop, and why

Six offered subjects pick a form and watch what it produces

They are all the same loop. map, filter and reduce are for…of with the bookkeeping named — and a named thing is a thing you can read at a glance.

The idea to land

map in JSX is a loop

You have been writing this since Module 2
<ul>
  {subjects.map((subject) => (
    <SubjectRow key={subject.id} subject={subject} />
  ))}
</ul>

An array of subjects in. An array of six <SubjectRow> elements out. React renders the array.

The same thing, spelled out
const rows = []
for (const subject of subjects) {
  rows.push(
    <SubjectRow key={subject.id} subject={subject} />
  )
}
return <ul>{rows}</ul>

Works identically. Three lines longer, and the rows array has to be declared, named, and remembered.

Students who learned for loops as a statement often do not recognise list rendering as iteration at all. It is the same loop. And key is how React tells one iteration from the next when the array changes.

The one that looks hardest

reduce is a loop with the accumulator named

In the codebase, for real
export function totalUnits(subjects: Subject[]) {
  return subjects.reduce(
    (sum, subject) => sum + subject.units,
    0
  )
}

The 0 is the starting value, and forgetting it on an empty array is the classic bug.

Line for line
let sum = 0
for (const subject of subjects) {
  sum = sum + subject.units
}
return sum

Same variable, same update, same result. reduce just moves the declaration into the call so it cannot be reused by accident.

When to use which: going from many to many, map. Many to fewer, filter. Many to one, reduce. Anything with an await inside it, for…of — and 3.5 shows why.

src/lib/ · src/features/
Same thing, three spellings

Arrows are shorter, not different

All three declare a function
// declaration — hoisted, has a name
function isFull(s: Subject) { return seatsLeft(s) === 0 }

// arrow, with a body
const isFull = (s: Subject) => { return seatsLeft(s) === 0 }

// arrow, implicit return — no braces, no `return`
const isFull = (s: Subject) => seatsLeft(s) === 0

Enroll uses declarations for exported functions and arrows for callbacks. Both, deliberately.

Where arrows earn their keep
onClick={() => add.mutate(subject)}
subjects.map((s) => s.units)
setTimeout(() => refetch(), 500)

A function passed to something else, used once, that does not need a name. Naming it would be one more thing to read.

Rule of thumb: a function you export gets a function declaration and a name. A function you hand to map or onClick gets an arrow.

The idea that explains hooks

A function remembers where it was born

The smallest possible example
function makeAdder(step: number) {
  return (n: number) => n + step
}

const addThree = makeAdder(3)
addThree(10) // 13

// makeAdder has already returned. `step` is gone
// from anywhere you could reach — except inside
// the function that was created there.
Which is why this works
function SubjectCatalog() {
  const [search, setSearch] = useState('')

  return <input onChange={(e) =>
    setSearch(e.target.value)
  } />
}

The arrow handed to onChange runs long after SubjectCatalog returned. It still reaches setSearch, because it closed over the scope it was written in.

This is the whole mechanism behind hooks. useState is not magic syntax — it is a function returning a value and a setter, and your handlers keep working because closures let them.

LO 3.4 · modularise

One job per file, and imports say so

Enroll's src/, and the rule for each folder
src/
  lib/          framework-free. No JSX in here, ever.
    api/        the one way in and out
    rules/      business rules, pure functions
  context/      state the client owns
  components/   reusable pieces
    ui/         generic: skeleton, empty, error
  features/     one folder per feature: screens + hooks
    enrollment/
    advising/
Export, then import
// units.ts — offers two things outward
export const UNIT_CEILING = 21
export function totalUnits(s) { … }

// SubjectCatalog.tsx — asks for them
import { totalUnits, UNIT_CEILING } from '@/lib/rules/units'

Anything without export is private to its file. That is the only encapsulation you need.

Why lib/ has no JSX: it is the part you can test without rendering anything. That is not tidiness — it is what makes lesson 3.8 possible.

A small thing that compounds

Why @/ exists

Relative paths
import { api } from '../../../lib/api/client'

Count the dots. Now move the file one folder deeper and count again.

Three levels of ../ tells you nothing about where the thing actually is.

An alias to the root
import { api } from '@/lib/api/client'

Reads as an address. Survives moving the importing file anywhere.

Configured twice, in vite.config.ts and tsconfig.app.json — the bundler and the typechecker each need telling.

Setting this up costs four lines and you notice it every day for a semester. The alias is in your project template too — use it.

LO 3.5 · serialize, deserialize

JSON is text. That is the whole idea.

A network carries bytes, not objects
// in your browser: a JavaScript object
{ code: 'CSci 153', units: 3 }

        ↓ JSON.stringify  (serialize)

// on the wire: a string
'{"code":"CSci 153","units":3}'

        ↓ JSON.parse      (deserialize)

// on the server: an object again
{ code: 'CSci 153', units: 3 }
What JSON cannot carry
  • Dates. They become strings — which is why the contract says format: date-time and you parse it yourself.
  • Functions. Silently dropped.
  • undefined. Dropped from objects entirely. null survives.
  • Comments. There is no such thing as a comment in JSON.

submittedAt arrives as "2026-08-19T02:19:05Z", a string. Calling .getFullYear() on it is the bug this slide exists to prevent.

The thing a request returns

A promise is a receipt, not a result

Three states, one direction
pending
The request is out. Nothing to show yet — this is your loading state.
fulfilled
A value arrived. await hands it to you.
rejected
It failed. await throws, which is why try/catch works on it.

Once it settles it never changes again. A promise resolves exactly once.

The mistake, and what it looks like
const res = fetch('/subjects')   // no await
console.log(res)
// → Promise { <pending> }

<p>{res}</p>
// → [object Promise]

You asked for the receipt and rendered it. [object Promise] on a screen always means a missing await.

await means stop here until this settles, then give me the value or throw. It only works inside a function marked async, and that function itself returns a promise — which is why await tends to spread.

Interactive · the cost of a loop with await in it

Three requests, two very different waits

Each request takes 300ms switch the strategy

Awaiting inside a loop makes requests queue. If they do not depend on each other, start them all and await the set — Promise.all. If each one needs the previous answer, sequential is correct and slow is the price.

Open the file

Every line of unwrap

src/lib/api/client.ts
export async function unwrap<T>(call): Promise<T> {
  const { data, error, response } = await call

  if (error !== undefined || !response.ok) {
    throw new ApiErrorException(
      normalizeError(error, response.status),
      response.status
    )
  }

  if (data === undefined) { throw … }

  return data
}
Four decisions in twelve lines
  • await call — the request is already in flight; this waits for it.
  • Destructuring — { data, error, response } pulls three names out of one object.
  • It throws instead of returning — because TanStack Query decides between its branches by whether the function threw.
  • A 2xx with no body throws too — that is a contract bug, not a state to design for.

Delete the throw and Query's error branch never fires: failures become silent. Try it, then put it back.

The half everybody forgets

A failed request is not an exception

The trap in plain fetch
const res = await fetch('/subjects')
const data = await res.json()
// 404? 500? This code cannot tell.
// fetch only rejects if the network failed.

A 500 is a successful fetch of an error page. You have to check res.ok yourself, every time.

Which is why the wrapper exists
if (error !== undefined || !response.ok) throw …

Written once, in one file, so no screen ever forgets it. Then every error reaching a component has the contract's shape: a code to branch on and a message to show.

Three very different failures — a documented 409, a dead network, a thrown exception — arrive as one shape. A component that had to tell them apart would grow three error paths.

HTML is text. The DOM is what the browser built from it.

Doing it by hand once is what turns React from magic into a labour-saving device, which is the difference between using it and being at its mercy.

textContent, not innerHTML, for anything a user typed. innerHTML with user input is how a script tag ends up in your page.

The two bugs everyone writes by hand

01 · Forgetting to clear
function render() {
  list.innerHTML = ''   // ← delete this line

  for (const subject of subjects) {
    list.appendChild(makeRow(subject))
  }
}

Without it, every render appends. Click twice and you have twelve rows; click ten times and the page has 60. The data is right and the screen is wrong.

02 · Forgetting to call it
subjects.push(newSubject)
// ← and nothing happens

The data changed and the screen did not. In React, state changing is the instruction to re-render — there is no call to forget.

Lesson 3.7 · LO 3.7

Three candidates,
one job

Pick one and defend it. "Most stars" is not a defence.

The judgment is the skill
The first question, before any comparison

Should this be a dependency at all?

Install it
  • It is genuinely hard and boring — date arithmetic, timezones, accessible dialogs, drag and drop
  • Getting it subtly wrong is expensive — auth, money, cryptography
  • It is a solved problem with a standard answer

Enroll installs openapi-fetch, @tanstack/react-query and react-router on exactly these grounds.

Write it
  • It is a few lines you fully understand — the unit-ceiling check is nine
  • It carries your design — the student card, the approval row
  • The library does forty things and you need one

lib/rules/units.ts is 90 lines and has no dependencies. It never will.

Every dependency is a permanent commitment: it can break, get abandoned, or change its mind about how it works. The cheapest dependency is the one you did not add.

Check yourself

Which one, and why

The skill nobody teaches

How to read documentation you did not write

First
The install and the first example

If the "getting started" example does not resemble your problem, this may be the wrong library. Two minutes, and it saves an afternoon.

Then
The API reference for one function

Read the whole signature. Optional parameters and defaults are where the behaviour you needed usually already exists.

Last
The changelog

Before any major upgrade. It is the only place that tells you what broke, and it is written for exactly this moment.

And when the docs are wrong or missing

Open node_modules/<package> and read the source, or the .d.ts file. It is allowed, it is often faster than searching, and the types cannot be out of date with the code the way prose can.

An agent is very good at this and still gets versions wrong. Paste the actual docs into context rather than trusting recall — the same principle as pasting the contract in Module 2.

Lesson 3.8 · one session

A test that has
never failed
proves nothing

Enough Vitest to not be lost in Module 5.

No learning outcome requires this
The anatomy

Three words, and one assertion

src/lib/rules/units.test.ts
describe('canAddSubject', () => {
  it('R2 · rejects an add past the ceiling', () => {
    const enrolled = [six(), six(), six()]  // 18 units

    const result = canAddSubject(six(), enrolled, 'draft')

    expect(result).toMatchObject({
      ok: false,
      code: 'UNIT_CEILING'
    })
  })
})
Read it as a sentence
  • describe — the thing under test
  • it — one claim about it, in words
  • expect — the claim, in code

Arrange, act, assert. Every test in the file has those three parts in that order.

The name is half the value. "returns an object" tests the language. "R2 rejects an add past the ceiling" tests a decision somebody made — and when it fails, the name alone tells you what broke.

Interactive · the run, and a deliberate break

Green means nothing until you have seen red

npm run test then break the rule on purpose

Change the ceiling to 24 and two tests fail with useful messages. That is the proof the tests are connected to the code. A suite that has never gone red might be asserting nothing at all.

Where the value is

Test the rules, not the framework

Worth testing
  • Pure functions with rules in them — the unit ceiling, capacity, duplicate detection
  • The boundaries — exactly 21 units, an empty array, a subject at capacity
  • Anything you got wrong once — a test is how a bug stays fixed

Enroll has 11 tests, all of them on lib/rules/.

Not worth your time here
  • That React renders a <div>
  • That map maps
  • Getters and setters with no logic in them
  • Chasing 100% coverage for its own sake

Coverage measures lines executed, not claims verified. 100% coverage with weak assertions is a comfortable lie.

The off-by-one test — an add landing exactly on 21 is allowed — is the most valuable one in the file. Boundaries are where bugs live, which is why every rule gets a test on each side of its edge.

The progression

Three kinds of test, arriving in order

KindWhenWhat it proves, and what it costs
UnitNow · 3.8 One function does what its name claims. Milliseconds to run, so you run them constantly.
ComponentModule 5 A component renders the right thing for a given state. Needs a fake DOM, so slower and more fragile.
End to endModule 5.3 A real browser completes a real flow against a real backend. The only kind that proves the app works — and slow enough that you keep few of them.
