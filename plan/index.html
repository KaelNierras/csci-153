CSci 153
Semester Plan

Five modules across eighteen weeks, with every topic mapped to the learning outcome that requires it — and every topic that no outcome requires, but the Final Activity Project does.

Required by a syllabus learning outcome The API contract — the through-line across modules 2, 4, and 5 No outcome covers it; added as a brief segment

The violet items are the gap analysis made concrete. The Final Activity Project specs depend on eight things the OBE syllabus never asks for — Git, server state, testing, Row Level Security, triggers, Edge Functions, end-to-end tests, and CI. Each gets roughly one session, folded into a module that already exists. None gets a lesson of its own, because the outcomes are fixed and the semester is full.

03

The Stack, End to End

Outlined Every piece of the toolchain, taught by opening the file it lives in — types, modules, JSON, the DOM, and how you know a function works. CO3
  • 3.1 The stack, named

    Open package.json and account for every line: what breaks if you remove it, and is it a library you call or a framework that calls you?

     LO 3.7
  • 3.2 TypeScript in five ideas

    Annotations, unions, optional and nullable, let vs const — read off the generated schema.d.ts, which nobody wrote by hand.

     LO 3.1, 3.2
  • 3.3 Arrays, objects, iteration

    for…of first, then map / filter / reduce on the enrollment data. The idea to land: map in JSX is a loop.

     LO 3.1, 3.3

    Closures explain hooks; import/export explains why lib/ differs from hooks/ differs from components/.

     LO 3.4
  • 3.5 JSON, fetch, and await

     LO 3.5
  • 3.6 What React does for you

    The subject list twice in one session — createElement by hand, then React. Fine for five rows; the lesson is the sixth.

     LO 3.6
  • 3.7 Choosing a library

    npm, semver, lockfiles — then three candidate packages for one job: downloads, last publish, issues, bundle size, shipped types. Pick one and defend it.

     LO 3.7
  • 3.8 Does it actually work? — briefly

    Vitest, ~1 session, on the reference app's unit-ceiling function — a pure function with no UI and no database. Watch it fail first. A test that has never failed proves nothing.

Backend Development

Outlined Schema, Row Level Security, and the functions that implement the contract. CO4
  • 4.1 Modeling a relational schema

    Tables, keys, relationships, normalization — worked from the group's own specification, §6.

     LO 4.1
  • 4.2 Migrations

    Schema as versioned, reviewable files — not clicks in a dashboard nobody can diff.

     LO 4.1

     LO 4.2
  • 4.4 Row Level Security — briefly

    The most important uncovered topic. Every authorization claim in all three specs rests on it. Demonstration: read another user's row with the anon key, watch it come back empty — then disable the policy and watch everything return.

     No LO
  • 4.5 Constraints and triggers — briefly

    Capacity ceilings, zero-gap adviser continuity, cached rollups, append-only audit logs. Why "the frontend validates it" is not an answer to "what stops a bad row."

     No LO
  • 4.6 Edge Functions — briefly

    Where secrets and multi-step writes live. Demonstration: put a key in a VITE_ variable, build, and find it in the bundle with devtools.

     No LO
  • 4.7 Implementing the contract

    Groups don't design an API here — they were handed one in week 3, by themselves. contract:check passes, or the module isn't done.

Web Application Integration

Outlined Validation, integration, CI, and a deployed application. CO5

10–17 Weeks
Development phase

No new lectures. Four two-week sprints building the Final Web Project, with the instructor in the room for all five contact hours a week. Three ~45-minute clinics sit inside it — end-to-end testing (week 12), CI (week 13), and deployment (week 15) — each taught in the week it is applied rather than eight weeks early.

Sprint 1 · 10–11 Schema, migrations, RLS Your own system's data model. Contract v2 where week-5 decisions were wrong. Gate: another group's account cannot read your rows — demonstrated, not claimed.
Sprint 2 · 12–13 Endpoints & integration CRUD, Edge Functions, first screens on the real backend. Gate: contract:check passes and CI is required before merge.
Sprint 3 · 14–15 Screens, validation, deploy Remaining screens, both validation layers, staging deployment. Gate: reachable at a URL by someone not in the group.
Sprint 4 · 16–17 Hardening & submission Test cases cleared, 12-point QA on every screen. Gate: Codebase Assessment and the Final Web Project.
18Week
Final examination

One document, carried across three modules

This is what makes the course hold together rather than being five unrelated units. The same OpenAPI file is written once and returned to twice.

ModuleRoleWhat happens to it
02ConsumeTyped wrapper and screens, running against a mock. The implementation does not exist yet.
04ImplementSchema, policies, and functions that satisfy the same document.
05IntegrateSwap the mock for the real base URL. Nothing else changes.

Known tension, stated in advance. The contract is authored in weeks 4–5, but schema modeling isn't taught until week 7. Groups will commit to request and response shapes before they have learned to model the data behind them, so breaking changes in sprint 1 are expected rather than exceptional — versioning the change and reviewing it is the method, not a failure of it. What would be a failure is silently editing the frontend to match a drifted backend.
