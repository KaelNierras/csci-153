A framing note, said out loud early

"Create a backend server" — with no server

What CO4 asks for

A backend server with RESTful API endpoints for database operations.

The classical answer is Express or Django: you write route handlers, they talk to a database, you deploy the process.

What this course does

Supabase. Postgres, plus PostgREST turning your tables into REST endpoints, plus Edge Functions for anything that needs code.

You still model a real schema and still produce real CRUD endpoints. What changes is that authorization moves into the database.

This is not a shortcut. It is the harder, more honest version — because when the endpoints are generated, the only thing protecting your data is the policy you wrote. There is no route handler to hide a forgotten check inside.

Four pieces, and what each is for

What "the backend" means here

Postgres · the tables

Your schema, written as migration files. Constraints and triggers enforce the rules a client cannot be trusted with.

PostgREST · the endpoints

Every table becomes a REST endpoint automatically. You write no route handlers, which means you cannot forget one.

RLS · the enforcement

A policy is a WHERE clause the database adds to every query for you. This is the entire authorization story.

Edge Functions · the exceptions

Anything needing a secret, a privileged write, or several statements that must succeed together.

Two of these four are not in any learning outcome — RLS and Edge Functions — and your project cannot work without them. They get short, practical sessions.

Three problems, and they are not stylistic
  • Update. Maria changes her name — three rows to fix, and if you miss one the database now disagrees with itself.
  • Insert. A new subject nobody has enrolled in yet cannot be recorded at all. There is no row to put it in.
  • Delete. Jose drops PE 4 and the only record that PE 4 is worth 2 units disappears with it.

Every one of these is the same bug: a fact is stored more than once, or in the wrong place entirely.

Pulling the facts apart

Step through it each step fixes one specific failure

You do not need the formal definitions of 1NF, 2NF and 3NF to do this well. You need one question, asked repeatedly: "if this fact changes, how many rows do I have to touch?" More than one is the smell.

The vocabulary

Keys, and the three relationships

Two kinds of key
create table subjects (
  id uuid primary key default gen_random_uuid(),
  code text not null,
  units int not null
);

create table enrollment_items (
  enrollment_id uuid references enrollments(id),
  subject_id    uuid references subjects(id),
  primary key (enrollment_id, subject_id)
);

Primary key — this row's identity. Foreign key — a pointer to another table's identity, which the database will not let you break.

One to many · the common case

One student has many enrollments. The foreign key goes on the "many" side — enrollments.student_id. This is the shape you will use most.

Many to many · needs a third table

An enrollment has many subjects; a subject appears in many enrollments. Neither side can hold the key, so enrollment_items exists to hold the pairs.

One to one · rare, and usually a mistake

If two tables have exactly one row each per thing, ask why they are two tables.

When the rule bends

Storing a total, on purpose

Compute it
select sum(s.units)
from enrollment_items i
join subjects s on s.id = i.subject_id
where i.enrollment_id = $1

Cannot be wrong. It is derived from the truth every time you ask.

Costs a join on every read, and the adviser queue reads it for forty students at once.

Store it
enrollments.total_units int not null default 0

One column, instant read, and the queue query gets simple.

And now it can be wrong. Any write that changes the items and forgets the total leaves the database disagreeing with itself.

Enroll's contract has totalUnits on the enrollment, so it is stored — and a trigger maintains it, not the application. That is lesson 4.5. Duplication with an automatic guardian is a decision; duplication maintained by hand is a bug waiting.

Lesson 4.2 · LO 4.1

sequence of files,

If it is not in a migration, it does not exist.

supabase/migrations/
The habit to break in week 7

Clicking works, until there are four of you

Clicking in the Supabase UI

Fast, and completely invisible. Nobody else's database changes.

No answer to "who added this column, and when, and why".

No way to review it before it happens. No way to undo it.

Your teammate's local database is now different from yours, and the bug only happens on one machine.

A migration file

A .sql file in the repository, in a pull request, reviewable like any other change.

git log answers who, when, and — if the message is good — why.

Every environment applies the same ordered list, so every database is the same database.

It is code. It gets the same treatment as code.

The rule for the semester: if a schema change is not in a migration file, it did not happen — and it will be gone the next time anyone resets.

The loop you will run all module

Write, apply, verify, commit

One change, one file
supabase migration new add_enrollment_status
# creates:
supabase/migrations/20260819021905_add_enrollment_status.sql
Why the timestamp matters

Migrations run in filename order, and the timestamp is what guarantees that order is the same for everyone.

It also means two people creating migrations on the same afternoon do not collide — the names differ by seconds.

Forward only
create type enrollment_status as enum (
  'draft', 'submitted', 'approved', 'returned'
);

alter table enrollments
  add column status enrollment_status
  not null default 'draft';
Two rules that save you

Never edit a migration that has been applied anywhere but your laptop. Others have already run it; changing it means their database and yours diverge silently. Write a new one.

Adding a non-null column needs a default, or the existing rows have nothing to put there and the migration fails.

Locally first, always
supabase db reset   # replay every migration from empty

db reset is the honest test: it proves the whole sequence works from nothing, which is what a new teammate and a fresh environment will do.

Then push
supabase db push    # apply new migrations to the hosted project

If db reset fails, your migration is broken even though your database looks fine. That gap is where "works on my machine" lives.

The schema changed, so the types must
supabase gen types typescript --local \
  > src/lib/supabase/database.types.ts
You have seen this exact pattern

Module 2 generated TypeScript from openapi.yaml. This generates TypeScript from your migrations. Same rule: the schema is truth, the types are downstream, and editing the generated file by hand is always a mistake.

The migration and the types go together
git add supabase/migrations/ src/lib/supabase/database.types.ts
git commit -m "feat(db): add enrollment status enum"
Why in one commit

Committing the migration without the regenerated types leaves a commit where the code and the database disagree. Anyone who checks out that commit gets type errors that are not their fault.

CI regenerates and fails if they drifted — so this is checked, not trusted.

Say this part out loud

Generated endpoints do not ask who you are

A table with RLS off
GET /enrollments

Returns every enrollment in the system, to anyone holding the anon key — which is compiled into your frontend bundle and readable by anybody who opens devtools.

Not a hypothetical. This is the default state of a new table.

What you might expect to protect you
  • The route guard — runs in the browser. Deleted with devtools in Module 2.
  • The frontend never requesting it — irrelevant. The endpoint does not care what your UI does.
  • The anon key being secret — it is not secret. It is in the bundle by design.

The only thing that protects a row is a policy on the table. That is the next lesson, and it is the most important hour in this module.

Getting the contract's shape back out

One request, nested rows

Your contract promised this shape
{
  "id": "…",
  "status": "draft",
  "totalUnits": 11,
  "subjects": [
    { "code": "CSci 153", "units": 3 },
    { "code": "Math 111", "units": 5 }
  ]
}

A nested array — and your schema has that split across three tables.

PostgREST follows the foreign keys
GET /enrollments
  ?id=eq.abc
  &select=id,status,total_units,
    enrollment_items(subjects(code,units))

Because the foreign keys exist, the embed is possible. The relationships you declared in 4.1 are what make this work — a schema without them cannot be queried this way at all.

Notice the mismatch: the database says total_units, the contract says totalUnits. Something has to reconcile that — a view, an alias, or a mapping layer. Decide where, once, and do it everywhere. Half-and-half is the worst option.

Lesson 4.4 · one to two sessions

The layer
everything else
was pretending to be

Every authorization claim in your project specification rests on this.

No learning outcome requires this
The whole idea, in one sentence

A policy is a WHERE clause the database adds for you

What you write
alter table enrollments enable row level security;

create policy "students read their own"
  on enrollments for select
  using ( student_id = auth.uid() );
What the client sends, and what actually runs
-- the request
select * from enrollments;

-- what Postgres executes
select * from enrollments
where student_id = auth.uid();

The client cannot see the added clause, cannot remove it, and cannot ask for the version without it.

auth.uid() is the id from the verified JWT. Not a value the client sends as data — a value the database extracts from a signed token it checked itself. That distinction is why this works at all.

Interactive · the same query, four identities

Who sees what

select * from enrollments switch identity, and toggle the policy off

The detail that surprises everyone: a blocked read comes back empty, not forbidden. There is no 403 — the rows simply are not in the result. Absence of data is what enforcement looks like.

The distinction that causes the most confusion

using reads. with check writes.

using — which existing rows can I touch?
create policy "students read their own"
  on enrollments for select
  using ( student_id = auth.uid() );

Applied to select, update and delete — the operations that need to find a row before acting on it.

with check — is this new row allowed?
create policy "students insert their own"
  on enrollments for insert
  with check ( student_id = auth.uid() );

Applied to insert and update — evaluated against the row as it will be.

The bug this prevents

An update policy with only using lets a student find their own enrollment and then change student_id to somebody else's. They were allowed to touch the row; nobody checked what they turned it into. Update policies need both clauses.

How to organise them

One policy per role, per operation

Enroll's enrollments table, in full
-- R7 · a student sees only their own
create policy "student select own" on enrollments
  for select using ( student_id = auth.uid() );

-- R5 · and edits it only while it is a draft
create policy "student update own draft" on enrollments
  for update
  using  ( student_id = auth.uid() and status = 'draft' )
  with check ( student_id = auth.uid() );

-- R8 · an adviser sees their own advisees
create policy "adviser select advisees" on enrollments
  for select using (
    exists (
      select 1 from students s
      where s.id = enrollments.student_id
        and s.adviser_id = auth.uid()
    )
  );
Why many small ones beat one clever one
  • Policies for the same operation are OR-ed. A student matching one and an adviser matching another both get through, with no shared condition to get wrong.
  • Each one is readable on its own, and its name says what it is for.
  • Deleting a role means deleting its policies — not editing a condition four roles depend on.

Notice R5 is enforced here too, not only in the UI. The status = 'draft' in the using clause is what actually stops an edit after submission.

The key that ignores everything

One key bypasses every policy

Two keys, and what each is for
anon · the public key
Ships in your frontend bundle. Anyone can read it. Every policy applies to it. That is fine, and it is the design.
service_role · the master key
Bypasses RLS entirely. Every row, every table, no policy evaluated.
Where the service role may appear
  • Inside an Edge Function, from a secret
  • In a CI job, from a repository secret
  • In any VITE_ variable
  • In any file the bundler can see
  • In a commit, ever — even a deleted one

A key in git history is a leaked key, whether or not the commit is still there.

If a service-role key reaches a browser, your entire database is public — every policy you wrote becomes decoration. Lesson 4.6 demonstrates exactly how it gets there.

How you know it works

Prove it from the other account

The five-minute check, per table
Sign in as student A. Read your own row.
You get it. The policy allows what it should.
With A's token, request B's row by id.
Empty. Not an error — empty.
Disable the policy. Request it again.
Everything comes back. Now you know the policy was the thing doing the work.
Re-enable it. Try to write to B's row.
Rejected — and if it is not, your update policy is missing with check.
Do it with a REST client, not your app

Your app sends requests your UI decides to send. A REST client sends whatever you type — including the request an attacker would send. Only one of those is a test.

Sprint 1's gate is this demonstration, not a claim that policies exist. Another group's account cannot read your rows, shown live.

Rules the table enforces itself

Four constraints that do most of the work

In Enroll's schema, for real
create table enrollment_items (
  enrollment_id uuid not null
    references enrollments(id) on delete cascade,
  subject_id uuid not null
    references subjects(id) on delete restrict,

  -- R3 · a subject at most once per enrollment
  primary key (enrollment_id, subject_id)
);

alter table subjects
  add constraint units_sane
  check (units between 1 and 6);

alter table subjects
  add constraint capacity_positive
  check (capacity > 0);
What each one buys
  • not null — the column always has a value. Cheapest constraint there is.
  • check — a value must satisfy an expression. Where most business rules can live.
  • unique / composite primary key — no duplicates, ever, from any code path.
  • references — a pointer that cannot dangle.

The two on delete choices are a design decision, not a default. Deleting an enrollment should take its items with it — cascade. Deleting a subject that people are enrolled in should be refused — restrict.

Interactive · try to insert a bad row

Which layer catches it

insert into … pick a bad write and see what rejects it

Notice how many are caught by the table itself, with no code involved. A constraint is a rule that holds no matter which client, which endpoint, or which bug tries to break it — including the ones you have not written yet.

When a constraint is not enough

A trigger maintains what a constraint cannot express

R2 · the unit ceiling, enforced where it counts
create function check_unit_ceiling()
returns trigger as $$
declare total int;
begin
  select coalesce(sum(s.units), 0) into total
  from enrollment_items i
  join subjects s on s.id = i.subject_id
  where i.enrollment_id = NEW.enrollment_id;

  if total > 21 then
    raise exception 'UNIT_CEILING: % units exceeds 21', total;
  end if;

  return NEW;
end $$ language plpgsql;

create trigger enforce_ceiling
  after insert on enrollment_items
  for each row execute function check_unit_ceiling();
Why a check cannot do this

A check constraint sees one row. The unit ceiling is a fact about all the rows for an enrollment, so it needs a query — and that means a trigger.

The other job triggers do

Maintaining the stored total_units from 4.1. Every insert or delete on enrollment_items recomputes it, so the duplicated value cannot drift from the truth.

This is what makes deliberate duplication safe rather than a liability.

Now the ceiling exists in three places — the UI in units.ts, this trigger, and the contract's documented 422. That is not redundancy: the first is a courtesy, the second is enforcement, the third is the agreement between them.

The decision, as a table

Which layer should hold this rule?

The ruleWhereWhy there
Units must be 1–6checkA property of one row. The table can answer it alone.
No duplicate subjectcomposite keyStructural. No code path can violate it, ever.
Total units ≤ 21triggerNeeds to see every row for the enrollment, so it needs a query.
Only your own recordRLS policyDepends on who is asking, which only the database knows for certain.
Submitting sets a timestamp and locks itEdge FunctionSeveral statements that must all succeed or all fail together.
Warn before you hit the ceilingthe UIA courtesy, so the user is told before the request. Never the enforcement.

The test for every row of this table: if someone bypassed your UI entirely and posted straight to the endpoint, would this rule still hold? If not, it is in the wrong layer.

Lesson 4.6 · one session

Where the secrets
and the transactions
live

Everything PostgREST cannot safely do for you.

No learning outcome requires this
When to write one, and when not to

Three reasons, and no others

Reason 01
A secret is involved

An API key, the service role, a signing secret. Anything that must never reach a browser has to run somewhere the browser cannot see.

Reason 02
Several writes must agree

Submitting an enrollment sets a status, stamps a time, and locks the items. All three, or none — a client doing them in sequence can stop halfway.

Reason 03
A privileged action

Something the caller is allowed to request but not to do directly, so it needs code checking the request first.

Otherwise: use PostgREST

A plain read, or a single-row write the caller is entitled to make, goes straight to the generated endpoint. Wrapping it in a function adds a deploy step, a cold start, and one more place for a bug — and buys nothing.

The rule, sayable in one line: plain read or single-row write → PostgREST. Secret, multi-step, or privileged → a function.

submitEnrollment, because it is all three reasons at once

What one actually looks like

supabase/functions/submit-enrollment/index.ts
Deno.serve(async (req) => {
  const auth = req.headers.get('Authorization')
  if (!auth) return err(401, 'UNAUTHORIZED', 'Sign in first.')

  // the caller's token — so RLS still applies to reads
  const client = createClient(URL, ANON, {
    global: { headers: { Authorization: auth } }
  })

  const { data: user } = await client.auth.getUser()
  if (!user) return err(401, 'UNAUTHORIZED', 'Sign in first.')

  // R6 · nothing to submit
  const { data: items } = await client
    .from('enrollment_items').select('subject_id')
  if (!items?.length)
    return err(422, 'EMPTY_ENROLLMENT',
               'Add at least one subject before submitting.')

  // one statement, so it succeeds or fails whole
  const { error } = await client.rpc('submit_enrollment', {
    p_term: body.term
  })
  if (error) return err(409, 'NOT_EDITABLE',
                        'This enrollment was already submitted.')

  return json(200, updated)
})
Three things to notice
  • It forwards the caller's token rather than using the service role. RLS still applies, so the function cannot accidentally act on someone else's data.
  • It returns the contract's error shape — code, message — with the documented status. The client has one error path, not two.
  • The multi-table write is one rpc call to a database function, which is what makes it atomic.

A function that returns a different error shape than PostgREST forces every screen to handle two formats. Match the contract, always.

The part to expect, and to do properly

Your week-5 contract will be wrong somewhere

Why it is wrong, and why that is fine

You specified data shapes in week 5. You learned to model data in week 7. Those two weeks are in that order on purpose — the contract had to exist before the frontend could be built.

So some shapes will turn out to be unrepresentable, or awkward, or missing a field the schema makes obvious.

The one unacceptable response

Silently editing the frontend to match whatever the backend ended up doing.

Now there is no agreement — just two halves that happen to line up today, and nothing to be wrong against tomorrow. You have thrown away the only thing keeping the two sides honest.

What to do instead
1 · change contract/openapi.yaml
2 · npm run contract:types        # the generated types move with it
3 · commit: feat(contract)!: rename load to enrollment
4 · in the PR body: who has to change what, and by when
5 · both sides approve — the FE half and the BE half

The ! is the whole point. It says out loud: someone's code stops working. That is a thing a group decides together, not a thing one person does on a branch.
