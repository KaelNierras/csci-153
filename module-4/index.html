Lesson 4.1 · LO 2.1

State that the whole
tree needs

Who is signed in? Almost every component wants to know — and passing it by hand does not scale.

The problem, measured

Prop drilling

Passing user down by hand

Drag the depth. Everything in red takes a user prop it never uses.

What that costs
  • Every prop type in between grows for no reason
  • Moving a component means re-threading the prop
  • A second piece of shared state doubles the noise
  • Testing any of them in isolation means inventing a user

Two levels of drilling is fine. Five is a signal.

The tool

Context: a value any descendant can read

Three parts, always
const SessionContext = createContext(null)

export function SessionProvider({ children }) {
  const [session, setSession] = useState(null)
  const value = useMemo(() => ({ session, setSession }), [session])
  return <SessionContext.Provider value={value}>
    {children}
  </SessionContext.Provider>
}

export function useSession() {
  const ctx = useContext(SessionContext)
  if (!ctx) throw new Error('useSession outside SessionProvider')
  return ctx
}
Why the hook, and why it throws

Nobody outside this file touches SessionContext — they call useSession().

The throw turns a confusing bug (session is mysteriously null) into a message that names the mistake: you forgot the provider.

Why useMemo

Without it, value is a new object every render — so every consumer re-renders for nothing.

The mistake everyone makes once

One context per concern — not one big one

One AppContext
{ session, theme, sidebarOpen,
  currentStudent, toasts,
  tableDensity, unreadCount }

Any field changing re-renders every consumer. Toggle the sidebar, re-render the 200-row table.

And it becomes a dumping ground — nobody can say what belongs in it.

Narrow contexts
SessionContext      → session, profile, role
AdviseeContext      → the record being worked on
PreferencesContext  → theme, density

Changing the theme re-renders what reads the theme. Nothing else notices.

Each has an obvious answer to "does this belong here?"

Your project spec already names the contexts your system needs, in §8 State Management. That list is short on purpose.

When useState stops fitting

Ordered transitions want a reducer

Four independent booleans
const [loading, setLoading] = useState(false)
const [error, setError]     = useState(null)
const [data, setData]       = useState(null)
const [retrying, setRetrying] = useState(false)

Nothing stops loading && error && data all being true at once. Meaningless, but representable — so it eventually happens, and the UI renders something nobody designed.

One state machine
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success', data: Subject[] }
  | { status: 'error', message: string }

Impossible combinations cannot be written down. Switch on status and every branch is designed.

The rule: independent toggles → useState. A sequence with rules about what follows what → useReducer. Door scanning (idle → scanning → resolving → accepted / duplicate / rejected) is the second kind.

Guarding routes — and what that is worth

A route guard is a redirect, not a lock

The guard
function RequireRole({ role, children }) {
  const { session, profile, status } = useSession()
  if (status === 'loading') return <FullPageSkeleton />
  if (!session) return <Navigate to="/login" replace />
  if (profile.role !== role) return <Navigate to="/" replace />
  return children
}

Note the loading branch. Without it, every refresh flashes a signed-in user to /login while the session resolves.

Say this out loud

This runs on the user's machine, in a bundle they can read and edit. Devtools deletes the check.

It keeps an honest user off a screen that would confuse them. It stops an attacker from nothing.

Real enforcement is Row Level Security in the database (Lesson 3.3). Guards are for usability; the server is for security.

LO 3.5 · Built against the spec, not invented

The typed client

src/lib/api/client.ts
import createClient from 'openapi-fetch'
import type { paths } from '../../../contract/generated/schema'

export const api = createClient<paths>({
  baseUrl: import.meta.env.VITE_API_BASE_URL,
})

api.use({
  onRequest({ request }) {
    const token = getAccessToken()
    if (token) request.headers.set('Authorization', `Bearer ${token}`)
    return request
  },
  onResponse({ response }) {
    if (response.status === 401) redirectToLogin()
    return response
  },
})

The <paths> generic is the trick: it is the generated type, so an endpoint that is not in the spec will not compile.

What belongs in the interceptor
  • Attaching the auth token
  • Normalising errors into one shape
  • Handling 401 globally
  • The base URL — the one line you change in Lesson 4.5
What does not
  • Business rules
  • Anything screen-specific
  • Silent retries that hide a real failure
The idea this lesson exists for

Server data is not component state

Treating it as component state
const [subjects, setSubjects] = useState([])
useEffect(() => {
  api.GET('/students/{id}/load', …)
     .then(r => setSubjects(r.data.subjects))
}, [id])
  • Loading state costs a second useState; error a third
  • Two screens on the same data fetch it twice
  • After a mutation, nothing knows to refetch
  • Change id twice quickly and the wrong response can win
Treating it as a cache
const load = useQuery({
  queryKey: ['getStudentLoad', id],
  queryFn: () => api.GET('/students/{id}/load', …),
})
  • isPending, isError, data — free
  • Two screens, same key, one request
  • Invalidate the key; everything refetches
  • Out-of-order responses handled for you

The shift: the data lives on a server. You hold a copy, and copies go stale. Every problem on the left comes from pretending otherwise.

Interactive · cache and invalidation

Keys come from the contract

The cache, live run a mutation and watch what goes stale

Key = operationId + parameters. Then invalidation is something you look up rather than remember — the practical reason the contract has stable operation names.

The decision that keeps both clean

Which tier does this state belong to?

The stateWhere it goesWhy
The signed-in session and roleContextClient-owned, needed everywhere, changes rarely.
A student's enrolled subjectsQueryServer-owned — it changes without you, so it must be refetchable.
Which advisee is being viewedContextAn id the client chose. The record it points at is a Query.
Theme and table densityContextClient-owned preference, persisted locally.
The approval queueQueryServer-owned, and shared — another organiser may be approving right now.
Whether a modal is openuseStateOne component's concern. It never crosses the tree.

The failure to avoid: fetching with Query, then copying the result into Context "so others can see it" — now you hand-sync two copies. Two components needing the same server data use the same query key.

Lesson 4.3 · LO 2.2

Now with
real latency

Module 1's states were drawn. These ones actually happen, at times you do not control.

What changes now

A mockup has no waiting in it

Under 100ms
Feels instant

Show nothing. A spinner that flashes for 80ms reads as a glitch.

100ms – 1s
Needs an acknowledgement

A skeleton shaped like the coming content, so the layout does not jump.

Over 1s
Needs progress

Say what is happening. On campus wifi this is the normal case.

Test on the network your users actually have

Devtools → Network → Slow 3G, then use your app for two minutes. What localhost hid becomes obvious: the layout shift, the double-clickable button, the empty state that flashes before data lands.

Loading, done properly

A skeleton is the shape of what is coming

Centred spinner

Says "something is happening" and nothing else.

When data lands, the layout appears at once and everything jumps.

The wait feels longer than it is.

Skeleton

Occupies the space the content will, so nothing moves.

Shows structure before content — the eye starts reading early.

Shortens the perceived wait. Cost: building it once.

Build the skeleton from the real component, reusing its spacing and sizes. If the two drift apart, the layout jumps again and you have the worst of both.

The two states that get defaulted

Empty and error are designed, not printed

Empty — three kinds, three answers
Nothing yet
"No reviews yet. Be the first." — plus the button. An opportunity, not an apology.
Nothing matched
"No students match maria in Computer Science." — echo the filters, offer to clear.
Nothing permitted
Say the account cannot see this, and who to ask. Never a table that looks broken.
Error — what went wrong, and what now
  • "Something went wrong"
  • "Error: undefined"
  • A raw stack trace
  • A dead end with no way forward
  • "Could not load your subjects." + Retry
  • "You are signed out." + Sign in
  • "Too many requests — try again in a minute." (the 429)

Each one is a documented response in your contract. The spec lists the errors your UI must render.

LO 2.2 · cross-device

Mobile-first is a default, not a media query

Tailwind breakpoints are min-width
<div class="grid grid-cols-1
            md:grid-cols-2
            lg:grid-cols-3 gap-4">

Unprefixed = the phone. Prefixed classes add capability as the screen grows.

The table problem

A 7-column table cannot shrink to 320px. Best: collapse each row into a card below md. Otherwise scroll it inside its own container — never the page body.

The floor, and how to check it
  • 320px with no horizontal scroll on the body
  • 200% zoom still usable — same problem as a small screen, and a WCAG requirement
  • Tap targets 44px or larger
  • Nothing important behind hover — phones have none

Two of the project systems are used on a phone, standing up — a guest checking an RSVP, staff scanning at a door. Mobile is the real case there, not the fallback.

Lesson 4.4 · LO 5.1

Both layers,
for different reasons

Not redundancy. Two jobs that happen to look alike.

The distinction that makes the duplication sane

One is kindness. One is enforcement.

Client · a user-experience affordance

Tells the user what is wrong while they are still looking at the field, before a round trip.

  • Instant, and specific to the input
  • Saves a request that was going to fail
  • Runs on a machine the user controls

Zod plus React Hook Form, in Enroll.

Server · the actual rule

Decides what is allowed to exist, no matter who is asking or what they are asking with.

  • Constraints, triggers and policies, from Module 3
  • Applies to your app, a REST client, and a script
  • Runs somewhere the user cannot reach

The only one of the two that is load-bearing.

You have met this shape twice already: a route guard is not RLS, and units.ts is not the trigger. Same principle, third time — the client copy is a courtesy, the server copy is the truth.

Interactive · post around the form

Which layer actually stops it

A bad enrollment, sent four ways pick a path and a bad value

Run this in class with a REST client. Every rule that only lives in the form is demonstrably not a rule — and the ones that survive are the ones you can defend.

The client half, written once

A schema, not a pile of if-statements

The shape, and the messages, together
const returnSchema = z.object({
  reason: z.string()
    .trim()
    .min(10, 'Say what needs changing — at least 10 characters.')
    .max(500, 'Keep it under 500 characters.')
})

type ReturnForm = z.infer<typeof returnSchema>

z.infer gives you the TypeScript type from the schema, so the form's type and its validation cannot disagree.

Where the numbers come from

The min(10) is not invented here. It is R9 in your project context and minLength: 10 in the contract — the same rule, written in three places on purpose, each doing a different job.

The error message is part of the design. "Invalid input" tells the user nothing. Write the message you would want if you were stuck on that field at 11pm.

When the server rejects it anyway

A server error has to land on a field

The lazy version
catch (e) {
  toast.error('Something went wrong')
}

The user has a form in front of them, a specific problem, and a message that helps nobody. They will try again identically.

Using the contract's error code
if (err.body.code === 'UNIT_CEILING') {
  setError('subjectId', {
    message: err.body.message   // already user-facing
  })
}

The message lands on the control that caused it. This is why the contract has a machine-readable code as well as a human message.

Every documented response in your contract needs a place to appear in the UI. That is point 9 of the 12-point QA, and this is the lesson where it gets paid for.

Lesson 4.5 · LO 5.2

The payoff,
or the bill

Whichever it turns out to be, week 5 decided it.

.env
Do this live, and time it

The whole integration

.env — before, and after
# weeks 3 – 12: the mock, served from the contract
VITE_API_BASE_URL=http://localhost:4010

# from sprint 2: your own backend
VITE_API_BASE_URL=https://xyz.supabase.co/rest/v1

One variable. No component changes, no query changes, no type changes — because every one of those was written against the contract, not against the mock.

Why nothing else moves
  • The types came from the contract, and the contract has not changed
  • The client's base URL was always one line in one file
  • Query keys are operation names, not URLs
  • Error handling was written against documented responses

Keep both .env files. Being able to flip between mock and real in front of the class is worth more than the ten seconds it takes.

Realistically, it will not be seamless

Two kinds of break, and both are findable

A contract violation

The backend did not implement what was agreed. Field named differently, a documented status never returned, a nullable field that is never null.

Whose bug: the backend's. The fix: make the implementation match the document.

A contract error

What was agreed turned out to be wrong. The shape cannot be produced from the schema, or it is missing something the UI genuinely needs.

Whose bug: the group's, in week 5. The fix: version the contract, tell both sides, regenerate.

This is the argument for contract-first, made concrete instead of asserted. Without the document, integration failures are "it does not work" and you bisect two codebases at once. With it, every failure is one of two specific, named things.

The two that surprise everyone

Problems the mock could not have

CORS
Access to fetch at 'https://xyz.supabase.co/…'
from origin 'http://localhost:5173' has been
blocked by CORS policy

The browser refuses a cross-origin response the server did not explicitly permit. Your local Prism allowed everything; a real host does not.

Fixed on the server, by allowing your origins. Never by "disabling CORS" in the browser — that only hides it on your machine.

A real token, for the first time
// weeks 3 – 12
'mock-token-student'

// now
eyJhbGciOiJIUzI1NiIsInR5cCI6…

The mock accepted any token. Supabase verifies a signature, checks expiry, and puts a real user id in auth.uid() — which is what makes every policy you wrote start applying.

A 401 you have never seen before usually means an expired session, not broken code.

Both of these are expected, and both are twenty-minute problems if you know their names. Losing an afternoon to CORS is what happens when you do not.

Clinic 5.3 · week 12 · 45 minutes

One test that
proves the app works

A real browser, a real backend, a real flow.

Taught in the week you apply it
What this adds to Lesson 2.7

Different question, different cost

A unit test asks…

"Does canAddSubject reject a 24-unit load?"

Milliseconds. No browser, no server, no database. You run hundreds without noticing.

It cannot tell you the button was wired to the wrong handler.

An e2e test asks…

"Can a student sign in, add three subjects, submit, and see the confirmation?"

Tens of seconds. Real browser, real requests, real rows. You keep a handful.

It is the only kind that proves the app works.

Both, in that ratio. Many cheap tests on the rules, a few expensive ones on the journeys that must never break — sign in, the core flow, and one permission boundary.

The one to write first

The flow your project exists to do

e2e/enrollment.spec.ts
test('a student submits an enrollment', async ({ page }) => {
  await loginAs(page, 'student')          // a real session

  await page.goto('/subjects')
  await page.getByRole('searchbox').fill('CSci')
  await page.getByRole('button', { name: 'Add' }).first().click()

  await page.goto('/enrollment')
  await expect(page.getByText('3 units')).toBeVisible()

  await page.getByRole('button', { name: 'Submit' }).click()
  await expect(page.getByText('Waiting for your adviser')).toBeVisible()
})

getByRole, not a CSS class. A test that breaks when you restyle a button was testing the wrong thing.

The rule that makes e2e worth doing

Run as an authenticated role. A test using the service role bypasses RLS — so it passes while your app is broken for every real user, which is worse than having no test.

And one test for the boundary
test('a student cannot open the adviser queue',
  async ({ page }) => {
    await loginAs(page, 'student')
    await page.goto('/advising')
    await expect(page).toHaveURL('/')
  })
The workflow your spec's §12 requires

Whoever writes the case does not write the test

01 · Project Manager
Files the case as an issue

Scenario, steps, expected result. In words, from the user's side. No code.

02 · A contributor
Writes the Playwright test

On a branch, in a PR that says Closes #47. Merging closes the issue.

03 · Everyone
CI runs it forever

The case stops being a document somebody remembers and becomes a check that cannot be skipped.

Why the split is deliberate

Someone writing both tends to write the test they know passes. Handing the case to a different person surfaces the ambiguity in the description — and an ambiguous test case is a requirement nobody actually agreed on.

This is graded. Activity 10 is test cases you did not write, implemented as tests that pass.

Clinic 5.5 · week 15 · LO 5.3

A URL a stranger
can open

Three places, and the secrets belong in exactly one of them.

Interactive · where each piece lives

Your app is not deployed in one place

Click a piece and see what belongs there — and what must not

The frontend is static files. No server runs your React code — a CDN hands the same bundle to everyone, and the browser does the rest. That single fact explains both the VITE_ secret problem and the next slide.

The bug every group hits within an hour

It works, until someone refreshes

What happens
1 · open /            → works
2 · click to /enrollment → works
3 · press F5          → 404

Clicking never asked the server for /enrollment — the router changed the URL in the browser. Refreshing does ask, and there is no file at that path, because there is only index.html.

The fix: send everything to index.html
# Vercel · vercel.json
{ "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
] }

# Netlify · _redirects
/*  /index.html  200

Now the server hands over index.html for any path and the router works out what to show, exactly as it did when you clicked.

Test it deliberately: deploy, navigate two levels deep, refresh, and share that URL with someone else. A link a marker cannot open is a deployment that does not count.

Before you call it deployed

The list

Run this on the real URL, not localhost
The two nobody does

05 · a fresh account. Your browser has a valid session from development. A new user hits code paths you have not run in weeks.

08 · a real phone on mobile data. Not a narrow browser window — an actual device, on a connection you do not control. It is how half your users will open it.

Put the URL in your README. A deployment nobody can find is indistinguishable from no deployment.
